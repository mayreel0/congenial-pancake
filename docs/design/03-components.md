# 온설 컴포넌트 기준

## 목적

온설의 컴포넌트는 화면을 빠르게 조립하기 위한 부품이 아니라, 서비스 톤을 반복해서 지키기 위한 단위다.

각 컴포넌트는 아래 정보를 가져야 한다.

- 언제 쓰는가
- 언제 쓰지 않는가
- 어떤 상태를 갖는가
- 어떤 데이터를 받아야 하는가
- 라이트/다크 모드에서 어떻게 보이는가

## 초기 컴포넌트 후보

### Button

역할:

- 명확한 사용자 행동을 실행한다.
- 링크처럼 보이는 이동과 제출 버튼을 구분한다.

상태:

- default
- hover
- focus-visible
- disabled
- loading

규칙:

- 버튼 텍스트는 한 줄로 유지한다.
- primary 버튼을 한 화면에 여러 개 두지 않는다.
- 준비 중 버튼은 실제 동작처럼 보이지 않게 한다.

### NoteCard

역할:

- 사용자가 남긴 위로 요청을 보여준다.

상태:

- unanswered
- answered
- reported-hidden
- compact

규칙:

- 요청 내용이 카드 안에서 가장 먼저 읽혀야 한다.
- 작성자 정보, 시간, 답변 수는 보조 정보다.
- 너무 긴 내용은 preview 높이를 정하고 일부만 보여준다.

### ReplyCard

역할:

- 위로 요청에 달린 답장을 보여준다.

상태:

- normal
- mine
- reported-hidden
- pending

규칙:

- 답장은 과한 장식 없이 문장 자체가 중심이 된다.
- “좋은 말”처럼 보이기보다 실제 사람이 남긴 짧은 답장처럼 보여야 한다.
- 답변 작성 UI와 표시 UI를 분리한다.

### ActivityStat

역할:

- 서비스가 오늘 실제로 움직이고 있다는 작은 힌트를 준다.

상태:

- normal
- empty
- loading

규칙:

- 숫자를 성과 지표처럼 과장하지 않는다.
- “오늘 18명이 남겼고 42개의 답장이 도착했습니다”처럼 문장형 표시도 허용한다.
- 랭킹, 인기, 경쟁 느낌으로 확장하지 않는다.

### RequestComposer

역할:

- 로그인 전에도 짧은 위로 요청을 작성하게 한다.

상태:

- empty
- typing
- saved-locally
- blocked-by-filter
- login-required-to-submit
- submitting

규칙:

- 입력창은 부담스럽지 않아야 한다.
- 너무 많은 도움말을 옆에 붙이지 않는다.
- 필터 경고는 공격적이지 않게 쓰되, 기준은 명확히 말한다.

### ReplyComposer

역할:

- 다른 사람의 요청에 답장을 작성하게 한다.

상태:

- empty
- typing
- saved-locally
- already-replied
- blocked-by-filter
- login-required-to-submit
- submitting

규칙:

- 한 사람이 한 요청에 답변 1개만 남기는 제약을 UI에서 분명히 보여준다.
- 자동 댓글 생성보다 작성 보조와 안전 필터를 우선한다.

## Story 작성 기준

반복될 컴포넌트는 Storybook story를 가진다.

각 story는 최소한 아래 상태를 포함한다.

- 기본 상태
- 긴 한국어 텍스트
- 비어 있는 상태
- 비활성 상태
- 다크모드에서 확인할 상태

상태가 많은 컴포넌트는 `play` function 또는 테스트 러너로 상호작용을 검증한다.

## 금지 기준

- 카드 안에 또 다른 독립 카드처럼 보이는 구조를 반복하지 않는다.
- 컴포넌트가 자신의 역할을 넘어 데이터 가져오기, 인증 판단, 신고 처리까지 직접 담당하지 않는다.
- 상태가 늘어날 때 props 이름을 임의로 계속 추가하지 않는다. 상태 모델을 먼저 정리한다.
- 컴포넌트마다 색과 spacing을 새로 고르지 않는다.
