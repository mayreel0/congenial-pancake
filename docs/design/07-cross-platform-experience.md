# 온설 웹/앱 경험 일관성 기준

## 목적

온설은 처음에는 웹으로 시작하지만, 나중에 앱으로 확장될 수 있다. 웹과 앱은 같은 기능을 복제하는 두 화면이 아니라, 같은 서비스 경험을 다른 환경에 맞게 제공해야 한다.

이 문서는 웹과 앱이 서로 다른 제품처럼 느껴지지 않게 하기 위한 기준이다.

## 기본 원칙

### 1. 핵심 경험은 같다

웹과 앱 모두 같은 핵심 흐름을 유지한다.

1. 오늘 있었던 일을 짧게 남긴다.
2. 답변이 부족한 요청을 먼저 본다.
3. 다른 사람에게 담백한 답장을 남긴다.
4. 내가 쓴 요청과 답장을 다시 확인한다.

플랫폼이 달라도 이 순서는 흔들리지 않는다.

### 2. 플랫폼 관습은 존중한다

일관성은 모든 UI를 똑같이 만드는 것이 아니다.

- 웹은 URL, 새 탭, 넓은 화면, 키보드 탐색을 존중한다.
- 앱은 하단 탭, 푸시 알림, 네이티브 입력 경험, 뒤로 가기 제스처를 존중한다.
- 같은 개념은 같은 이름을 쓰되, 배치는 플랫폼에 맞게 바꿀 수 있다.

### 3. 말투와 상태 모델은 공유한다

웹과 앱이 달라져도 아래는 공유한다.

- 기능 이름
- 버튼 문구
- 오류와 필터 안내의 톤
- 요청/답장의 상태 이름
- 신고/숨김/대기 상태의 의미

UI 모양보다 용어와 상태 의미가 더 중요한 일관성 기준이다.

## 공유해야 하는 것

### 디자인 토큰

웹과 앱은 가능한 한 같은 semantic token을 공유한다.

예:

- `color.background.default`
- `color.text.default`
- `color.text.muted`
- `color.action.primary`
- `color.border.default`
- `radius.control`
- `space.page`

플랫폼별 구현값은 달라도 이름과 역할은 맞춘다.

### 콘텐츠 규칙

아래 문구 원칙은 웹과 앱 모두 같다.

- 과하게 감성적인 표현을 피한다.
- AI가 자동으로 위로하는 듯한 문장을 피한다.
- 필터 안내는 분명하지만 차갑지 않게 쓴다.
- 준비 중 기능은 실제 동작처럼 보이지 않게 한다.

### 상태 정의

요청과 답장의 상태는 플랫폼 공통 개념으로 둔다.

요청 상태 후보:

- draft
- saved-locally
- submitted
- awaiting-reply
- answered
- hidden-by-report
- blocked-by-filter

답장 상태 후보:

- draft
- saved-locally
- submitted
- hidden-by-report
- blocked-by-filter
- already-replied

상태 이름은 구현 전에 다시 확정하되, 웹과 앱에서 서로 다른 의미로 쓰지 않는다.

## 달라도 되는 것

### 내비게이션

웹:

- URL 기반 route
- 브라우저 뒤로 가기
- 넓은 화면에서 목록과 상세 동시 표시

앱:

- 하단 탭 또는 stack navigation
- 앱 뒤로 가기 제스처
- 알림에서 특정 요청/답장으로 진입

### 입력 방식

웹:

- 키보드 입력
- submit 단축키 후보
- 브라우저 focus 상태

앱:

- 모바일 키보드
- 안전 영역
- 입력 중 화면 밀림
- 알림 권한 안내

### 알림

웹:

- 초기에는 알림 없이 시작할 수 있다.
- 나중에 웹 push를 고려한다.

앱:

- 답장 도착 알림이 핵심 가치가 될 수 있다.
- 단, 앱 알림은 후순위 기능이며 초기에 과하게 설계하지 않는다.

## 웹에서 앱으로 확장할 때 유지할 것

- 온설이라는 이름과 보조 문구
- 요청 작성의 짧고 낮은 부담
- 답변 부족 요청 우선 노출
- 한 사람 한 요청에 답변 1개 원칙
- 신고/필터 기준
- 담백한 위로 톤
- 다크모드 기본 고려

## 웹과 앱을 다르게 만들 수 있는 판단 기준

아래 중 하나에 해당하면 플랫폼별 차이를 허용한다.

- 플랫폼 기본 조작 방식과 맞지 않는다.
- 입력 또는 읽기 경험이 나빠진다.
- 화면 크기 때문에 같은 구조가 오히려 복잡해진다.
- 앱에서만 가능한 가치가 있다.
- 웹에서만 가능한 탐색성이 있다.

하지만 차이를 만들 때는 feature spec에 이유를 기록한다.

## Feature spec에 적어야 하는 내용

앱 확장을 고려해야 하는 기능은 spec에 아래를 적는다.

- 이 기능이 웹과 앱에서 같은 이름을 쓰는가?
- URL 또는 앱 navigation에서 어떤 위치를 갖는가?
- 로컬 저장 draft가 플랫폼별로 같은 의미인가?
- 알림이 필요한 기능인가, 후순위인가?
- 플랫폼별로 달라지는 UI가 있다면 왜 필요한가?

## Storybook과의 관계

Storybook은 웹 컴포넌트 도구지만, 앱과 공유할 수 있는 기준을 검증하는 데도 도움 된다.

- 용어와 상태 이름이 일관적인지 확인한다.
- 긴 한국어 텍스트와 빈 상태를 반복 검토한다.
- 토큰 이름이 플랫폼 공통 의미를 갖는지 확인한다.
- 앱 구현 전에도 웹 컴포넌트 story를 통해 서비스 톤을 먼저 고정한다.

나중에 앱을 만든다면 Storybook은 웹 구현 결과물이고, 앱 쪽은 별도 preview 도구를 사용할 수 있다. 그래도 디자인 원칙, 토큰 이름, 상태 의미는 같은 문서에서 출발한다.
