# 온설 반응형 레이아웃 기준

## 목적

온설은 PC, 태블릿, 모바일에서 같은 서비스로 느껴져야 한다. 반응형은 화면을 줄였을 때 깨지지 않게 하는 기술 처리가 아니라, 사용자가 어떤 기기에서든 짧게 남기고 답장을 읽는 흐름을 유지하는 UX 기준이다.

## 지원 범위

초기 웹은 아래 viewport 범위를 기준으로 설계한다.

- 모바일: 360px 이상
- 태블릿: 768px 이상
- 데스크톱: 1024px 이상
- 넓은 데스크톱: 1280px 이상

검증 기준 viewport:

- 390px 모바일
- 768px 태블릿
- 1024px 데스크톱
- 1440px 넓은 데스크톱

기준은 Tailwind breakpoint 이름에 종속되지 않는다. Tailwind를 사용할 때는 이 범위가 실제 사용자 경험 기준이고, `sm`, `md`, `lg`, `xl`은 구현 도구로 본다.

## 공통 원칙

### 1. 모바일 우선

온설의 핵심 행동은 짧은 글을 쓰고 답장을 읽는 것이다. 이 행동은 모바일에서 먼저 자연스러워야 한다.

- 작성 흐름은 모바일 1컬럼을 기본으로 설계한다.
- 데스크톱 레이아웃은 모바일 흐름을 확장한 형태여야 한다.
- 데스크톱에서만 가능한 정보 구조를 핵심 흐름으로 만들지 않는다.

### 2. 핵심 글은 항상 먼저 읽힌다

어떤 viewport에서도 요청과 답장이 보조 정보보다 먼저 읽혀야 한다.

- 요청/답장 본문은 카드 안에서 가장 눈에 띄는 텍스트다.
- 시간, 답변 수, 신고, 작성자 정보는 보조 정보다.
- 모바일에서 보조 정보가 본문보다 먼저 오지 않게 한다.

### 3. 정보 밀도는 기기별로 다르게 조절한다

모바일은 집중, 데스크톱은 비교와 탐색에 유리하다.

- 모바일: 하나의 요청 또는 작성 흐름에 집중한다.
- 태블릿: 목록과 선택된 내용을 느슨하게 분리할 수 있다.
- 데스크톱: 목록, 작성 영역, 답장 영역을 나란히 둘 수 있다.

단, 데스크톱에서도 한 화면에 너무 많은 요청을 동시에 노출하지 않는다.

## 레이아웃 패턴

### 모바일

권장 구조:

1. 오늘의 핵심 행동
2. 답변이 부족한 요청
3. 최근 요청/답장
4. 내 활동 또는 보조 정보

기준:

- 기본 1컬럼
- 좌우 여백 16px 또는 20px
- 터치 타겟 최소 44px
- 긴 한국어 문장은 줄바꿈이 자연스럽게 일어나야 한다.
- fixed bottom CTA는 입력 화면에서만 신중하게 사용한다.

피한다:

- 작은 카드 2컬럼
- 좁은 말풍선에 긴 문장 넣기
- 버튼 텍스트 줄바꿈
- 화면 하단을 계속 가리는 sticky UI

### 태블릿

권장 구조:

- 1컬럼 또는 느슨한 2컬럼
- 목록과 상세를 나누더라도 각 영역이 독립 카드처럼 과하게 분리되지 않게 한다.
- 작성 영역은 너무 좁게 만들지 않는다.

기준:

- 세로 태블릿은 모바일 확장으로 본다.
- 가로 태블릿은 데스크톱 전 단계로 본다.
- 작성 패널 폭은 최소 360px 이상을 확보한다.

### 데스크톱

권장 구조:

- 왼쪽: 우선 노출 요청 목록
- 오른쪽: 선택된 요청, 답장, 작성 영역
- 또는 랜딩처럼 정보가 적은 화면은 중앙 집중형 레이아웃

기준:

- 본문 최대 폭을 제한한다.
- 넓은 화면에서 콘텐츠가 과하게 벌어지지 않게 한다.
- 데스크톱이라고 해서 모든 정보를 동시에 보여주지 않는다.
- 반복 사용 화면은 랜딩보다 더 높은 정보 밀도를 허용한다.

피한다:

- 넓은 화면을 채우기 위한 장식용 카드 추가
- 3컬럼 이상으로 요청/답장을 쪼개기
- 핵심 작성 흐름을 화면 오른쪽 작은 패널에 밀어 넣기

## 컴포넌트별 반응형 기준

### NoteCard

- 모바일: 전체 폭 1컬럼
- 태블릿: 목록 안에서는 전체 폭, 요약 목록에서는 2컬럼 후보
- 데스크톱: 목록 영역에서는 compact variant 허용

긴 글은 preview 높이를 제한하고, 상세 화면에서 전체를 읽게 한다.

### ReplyCard

- 모바일: 요청 아래에 시간순으로 쌓는다.
- 데스크톱: 요청 상세 영역 안에서 읽기 폭을 제한한다.
- 답장이 많아져도 카드 간 shadow를 늘리지 않는다.

### Composer

- 모바일: 작성 영역이 화면의 주 작업이 된다.
- 태블릿: 작성 영역과 미리보기 또는 안내를 나눌 수 있다.
- 데스크톱: 목록과 작성 영역을 나란히 둘 수 있다.

작성 입력창은 어떤 viewport에서도 너무 낮거나 좁게 보이면 안 된다.

### ActivityStat

- 모바일: 숫자 카드보다 짧은 문장형 표시를 우선 검토한다.
- 태블릿/데스크톱: 2개 또는 3개 항목을 나란히 둘 수 있다.
- 숫자를 성과 지표처럼 과장하지 않는다.

## 검증 기준

새 화면 또는 주요 컴포넌트는 최소한 아래 viewport에서 확인한다.

- 390px x 844px
- 768px x 1024px
- 1024px x 768px
- 1440px x 900px

확인 항목:

- 가로 스크롤 없음
- 버튼 텍스트 줄바꿈 없음
- 본문과 보조 정보 겹침 없음
- 한국어 긴 문장 줄바꿈 자연스러움
- 터치 타겟 최소 44px
- 라이트/다크 모드 모두 읽기 가능

## Feature spec에 적어야 하는 내용

반응형 공통 규칙은 이 문서에 둔다. 하지만 기능별로 다른 판단이 필요한 경우 feature spec에 별도로 적는다.

예:

- 요청 작성 화면에서 모바일 CTA를 하단 고정으로 둘지 여부
- 데스크톱에서 요청 목록과 작성 패널을 나란히 둘지 여부
- 태블릿에서 1컬럼을 유지할지 2컬럼으로 전환할지 여부
- 신고/필터 안내가 작은 화면에서 작성 흐름을 얼마나 막는지

즉, 디자인 시스템은 공통 규칙이고 feature spec은 그 기능에서의 적용 방식이다.
