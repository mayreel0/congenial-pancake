# `/today` 재설계 구현 기록

## 구현 범위

`/today`를 기존 all-in-one 프로토타입 화면에서 기본 문구, 순환 온설 문구, 입력창, 제출 상태 중심 화면으로 바꿨다.

## 유지한 결정

- 순환 온설은 최근 온설 캐시를 우선 사용하고, 없으면 기본 샘플을 보여준다.
- 내가 방금 작성한 온설은 순환 온설에 즉시 넣지 않는다.
- 제출은 pending, 성공, 입력창 비움 lifecycle을 보여준다.
- 성공 피드백은 입력창 아래 인라인 문구가 아니라 레이아웃을 밀지 않는 toast로 보여준다.
- 모바일에서는 기본 문구와 순환 온설 문구를 중간에 두고, 입력창만 손이 닿기 쉬운 하단 근처에 배치한다. 키보드/safe-area 복잡도가 큰 fixed bottom 입력창은 아직 쓰지 않는다.
- 초기 화면에는 `누군가에게 답하기` 보조 링크와 이미지 버튼을 넣지 않는다.

## 구현 메모

- 최근 온설 선택은 `getRecentNonViewerRequests`와 `getTodayEntryMessages`로 분리했다.
- 제출 lifecycle은 `useOnseolPrototype` 안에서 `requestSubmitStatus`로 관리한다.
- 중복 제출 방지는 pending 상태와 별도로 ref guard를 둔다.
- 순환 온설 전환은 `RotatingOnseolLine`과 `onseol-soft-wipe` CSS로 분리했다. 문구 변경 시 element key를 바꿔 animation이 다시 시작되게 한다.
- 순환 온설 문구는 모바일에서 길이가 바뀌어도 입력창 위치가 흔들리지 않도록 2줄 기준 고정 높이와 줄 제한을 둔다.
- 입력 textarea는 작성량에 따라 자동으로 아래로 확장한다. 기본 1줄에서 시작하고 최대 높이를 넘으면 내부 스크롤로 전환한다.
- `prefers-reduced-motion`에서는 wipe animation을 끈다.

## QA 반영 메모

- `남겨졌어요`는 표현이 어색하고, 인라인으로 렌더링하면 성공 상태에서 UI 높이가 바뀐다.
- 성공 문구는 `온설을 남겼어요`로 바꾸고, 2초 후 사라지는 toast로 처리한다.
- toast는 fixed 위치에 렌더링해 입력 영역과 활동 요약의 레이아웃을 바꾸지 않는다.
- 모바일에서 toast가 입력 영역을 가릴 수 있으므로 `알림 닫기` 버튼으로 즉시 닫을 수 있게 한다.
- 모바일 `/today`는 화면 전체를 세로 grid로 쓰되, 문구 영역과 작성 영역을 분리한다. 문구 영역은 중간, 작성 영역은 하단에 두고 태블릿/PC에서는 자연스러운 중앙 흐름으로 되돌린다.
- 순환 온설은 전환 CSS만 두면 React가 같은 DOM node의 텍스트만 바꿀 수 있어 animation이 체감되지 않을 수 있다. 문구 변경 시 key를 바꿔 전환 animation을 재시작한다.

## 추가 시각/모바일 UX 기록

리뷰 중 모바일 실기기 확인을 위해 포트 포워딩으로 `/today`를 열어 보았다. 모바일에서 발생한 핵심 관찰은 단순한 반응형 너비 문제가 아니라 브라우저 주소창, safe area, 키보드, toast, 입력창 자동 높이, 순환 문구 높이가 모두 화면 세로 리듬에 영향을 준다는 점이다.

현재 구현이 크게 어색하다는 판단은 아니다. 다만 온설처럼 첫 화면의 요소가 적은 서비스는 작은 높이 변화, 전환 유무, toast 위치, 키보드 등장 시 압축 방식 같은 시각 디테일이 제품 완성도를 크게 좌우한다. 따라서 아래 내용은 즉시 전부 구현해야 하는 결함 목록이라기보다, 이후 위키와 디자인 시스템에서 반복 참조할 visual polish 기준으로 남긴다.

### Viewport와 키보드

- 모바일 브라우저의 상단 주소창과 탭 영역은 페이지의 실제 표시 영역을 계속 바꾼다. `100vh`만 기준으로 잡으면 주소창이 보일 때 빈 공간이 어색하게 느껴질 수 있고, 주소창이 접히거나 키보드가 열릴 때 시각적 중심이 갑자기 달라질 수 있다.
- 기본 높이는 `100dvh` 계열을 우선 고려한다. 단, iOS Safari와 Android Chrome의 동작 차이가 있으므로 `min-height: 100dvh`, safe-area padding, 실제 기기 QA를 함께 봐야 한다.
- 키보드가 열렸을 때 화면 높이를 더 섬세하게 맞추려면 `window.visualViewport` 기반 처리가 가능하다. `visualViewport.height`, `offsetTop`, `resize`, `scroll` 이벤트를 사용해 CSS 변수로 현재 표시 높이나 키보드 inset을 전달하는 방식이다.
- 다만 `visualViewport`는 브라우저별 차이가 있고 이벤트가 자주 발생하므로, 초기 구현에서는 모든 레이아웃을 JS로 제어하기보다 키보드가 열렸을 때 어색함이 큰 지점에만 제한적으로 적용하는 편이 낫다.
- 온설의 현재 방향은 기본 문구와 순환 문구를 너무 아래로 밀지 않고 중간에 두는 것이다. 입력창은 모바일에서 손이 닿기 쉬운 하단 쪽에 두되, 키보드가 열리면 남은 viewport 안에서 자연스럽게 위로 압축되어야 한다.
- 키보드 대응은 항상 필요한 고도화는 아니다. 현재 화면이 자연스럽다면 `100dvh`와 적절한 grid 배치로 유지하고, 실제 기기에서 키보드 등장 시 입력창이 가려지거나 상단 여백이 과하게 남는 경우에만 `visualViewport` hook을 추가하는 편이 낫다.

### 입력창 높이

- 모바일에서도 PC처럼 입력창은 줄이 바뀌면 위쪽으로 자연스럽게 늘어나야 한다.
- 입력창을 하단에 가깝게 둘 경우, textarea가 아래로만 커지면 화면 밖으로 밀리거나 버튼 위치가 흔들릴 수 있다. 하단 정렬된 composer 안에서 textarea 높이를 재측정하고, 최대 높이를 넘으면 내부 스크롤로 전환하는 구조가 필요하다.
- 입력창이 커지는 동작은 제출 버튼의 hit target과 함께 봐야 한다. 버튼은 글이 길어져도 눌릴 수 있어야 하고, pending 중에는 명확히 비활성처럼 보이되 실제 입력 상태와 disabled 조건이 어긋나면 안 된다.

### 순환 온설 문구

- 순환 문구는 최근에 올라온 온설을 캐싱해서 보여주고, 데이터가 없으면 기본 샘플을 fallback으로 둔다.
- 순환 문구의 목적은 사용자가 어떤 정도로 짧게 남겨도 되는지 감을 잡게 하는 것이다. 입력보다 강한 피드나 카드 목록처럼 보이면 `/today`의 핵심이 흐려진다.
- 문구 길이가 달라질 때 모바일 UI 높이가 바뀌면 입력창 위치가 흔들린다. 따라서 줄 수 제한, 고정 또는 최소 높이, line-clamp를 함께 사용해 문구 교체가 레이아웃을 밀지 않게 해야 한다.
- 기본 전환은 soft vertical wipe가 적합하다. 다만 텍스트만 바뀌고 DOM node가 유지되면 CSS animation이 다시 시작되지 않을 수 있으므로, 문구 변경 시 key를 바꾸거나 animation trigger를 명시적으로 갱신해야 한다.
- `prefers-reduced-motion`에서는 wipe를 끄고 즉시 교체 또는 아주 약한 fade로 대체한다.

### 제출 성공 피드백

- 성공 피드백을 입력창 아래 인라인 문구로 보여주면 성공 순간 UI 높이가 변한다. 사용자가 입력과 제출 lifecycle을 봐야 하는 화면에서는 이 변화가 생각보다 거슬릴 수 있다.
- 성공 메시지는 `온설을 남겼어요`처럼 담백한 문구가 낫다. `남겨졌어요`는 다소 어색하고 제품의 말투로 덜 자연스럽다.
- toast는 레이아웃을 밀지 않기 때문에 성공 피드백에 적합하다. 대신 모바일에서는 입력창이나 키보드와 겹칠 수 있으므로 위치, safe area, 닫기 버튼을 같이 설계해야 한다.
- toast는 자동으로 사라지되 즉시 닫을 수 있어야 한다. 모바일에서 toast가 입력 영역을 가리면 사용자가 기다리지 않고 지울 수 있어야 한다.

### 후속 구현 후보

- `visualViewport`를 감지해 `--visual-viewport-height` 또는 `--keyboard-inset` 같은 CSS 변수를 갱신하는 작은 hook을 검토한다.
- `/today`에서 키보드가 열린 상태, 주소창이 보이는 상태, 주소창이 접힌 상태, toast가 떠 있는 상태를 각각 모바일 QA 체크리스트에 넣는다.
- 순환 문구 전환 방식, 전환 시간, 전환 속도는 나중에 앱 설정 또는 내 정보 설정에서 사용자 설정 후보로 남긴다.
- 입력창 옆 액션 영역은 나중에 이미지 추가 버튼을 넣을 수 있도록 확장 가능하게 유지하되, 초기 화면에는 비활성 이미지 버튼을 노출하지 않는다.

## 네비게이션 구현 메모

- 랜딩과 서비스 네비게이션을 분리했다.
- 랜딩에는 `온설`, `로그인`, `웹에서 시작하기` 진입을 두고, 서비스 내부 메뉴 전체는 노출하지 않는다.
- 서비스 웹 네비게이션은 상단 nav로 두고, 모바일 네비게이션은 하단 탭이 아니라 상단 메뉴 버튼으로 둔다.
- `내 기록`은 웹의 주요 서비스 nav에 섞지 않고 우측 개인 영역에 둔다. 이는 이전 IA 결정인 `내 기록은 상단 우측에 따로 둔다`와 맞춘 것이다.
- `/today`에 서비스 네비게이션을 연결했다.
- `/answer`, `/read`, `/me`, `/login`은 이동 검증을 위한 placeholder로만 추가했다.
- 실제 인증, 내 기록 데이터, 읽기/답하기 본문 구현은 후속 PR로 남긴다.
- repo-local `.worktrees`, `.pnpm-store`, `.superpowers`는 ESLint 대상에서 제외했다. 특히 `.worktrees/**` 안의 Next 생성물이 lint에 포함되면 현재 PR과 무관한 `.next` 산출물 오류가 대량 발생한다.
- pre-PR review에서 desktop `/me` 접근과 landing landmark 구조가 지적되었다. `내 기록`은 우측 개인 영역 링크로 추가했고, 랜딩 header는 `<main>` 밖으로 이동했다.
