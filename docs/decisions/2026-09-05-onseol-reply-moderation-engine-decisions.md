# 온설 답장 사전 moderation 엔진 결정 기록

## 배경

온설은 짧은 위로 요청과 담백한 답장을 주고받는 서비스다. 기존 `apps/api-server/src/moderation`은 신고가 3명 이상 누적된 요청/답장을 자동 숨김 처리하는 사후 moderation만 담당한다. 이번 결정은 답장이 등록되기 전에 온설의 대화 원칙에 맞는지 검사하고, 필요하면 더 온설다운 문장으로 다시 쓰도록 돕는 사전 moderation 엔진의 범위를 정한다.

사용자는 위로 요청과 답장을 같은 기준으로 필터링하면 안 된다고 판단했다. 위로 요청은 아픈 감정과 부정적인 표현이 담길 수 있으므로 검열보다 작성 보조가 어울리고, 답장은 다른 사람에게 닿는 말이므로 더 엄격한 사전 검사 대상이 된다.

## 결정 1: 이번 범위는 moderation 내부의 답장 사전 검사 엔진으로 제한한다

`RepliesService.create()`, API 응답 형식, 프론트 UI, DB 스키마, 관리자 화면, 배포/인프라는 이번 범위에서 제외한다. 작업 대상은 `apps/api-server/src/moderation` 내부의 답장 언어 안전 검사 엔진과 그 요구사항이다.

### 근거

백엔드 등록 흐름까지 한 번에 연결하면 API 계약, 프론트 UX, 에러 처리, 저장 정책까지 같이 결정해야 해 범위가 커진다. 먼저 moderation 내부에서 판정 타입, 정책, LLM 호출 경계, 테스트 fixture를 안정화한 뒤 별도 작업에서 답장 등록 흐름에 연결하는 편이 안전하다.

## 결정 2: 위로 요청은 작성 보조, 답장은 moderation 대상으로 분리한다

위로 요청은 필터링보다 감정 키워드, 상황 태그, 받고 싶은 위로 유형 등을 통해 사용자가 글을 쉽게 쓰도록 돕는 방향으로 둔다. 답장은 사전 moderation 대상으로 삼는다.

### 근거

위로 요청은 사용자의 날것의 감정이 들어오는 영역이다. 이 영역에 답장과 같은 필터를 적용하면 온설이 숨 쉴 수 있는 공간이 아니라 표현을 막는 공간처럼 느껴질 수 있다. 반대로 답장은 다른 사람에게 직접 닿으므로 조롱, 비난, 평가, 감정 축소를 더 적극적으로 걸러야 한다.

## 결정 3: 기본 동작은 다시쓰기 제안, 심한 경우만 차단한다

답장 판정은 `allow`, `suggest_rewrite`, `block`, `uncertain` 네 가지로 둔다. 기본은 차단이 아니라 `suggest_rewrite`이며, 명백히 해로운 표현이나 온설의 목적을 벗어나게 만드는 표현만 `block`한다.

### 근거

온설의 moderation은 사용자를 벌주는 장치가 아니라 말이 상처로 닿지 않도록 돕는 장치여야 한다. 차갑거나 판단적인 말, 감정 축소, 원치 않는 해결책 제시는 차단보다 다시쓰기 제안이 적합하다. 욕설, 혐오, 위협, 신상 공개, 홍보, 갈등 조장 등은 등록 자체를 막는다.

## 결정 4: 리라이트는 짧고 담백한 비해결형 공감으로 통일한다

리라이트 suggestions는 `string[]`로 1-3개 제공한다. 문체는 "짧고 담백한 비해결형 공감"으로 통일한다.

### 근거

처음에는 "짧고 담백한 공감", "조금 더 따뜻한 위로", "해결보다 동행 중심" 같은 문체 옵션을 나눴지만, 실제 제품 규칙으로는 차이가 흐렸다. 온설에는 문체 옵션보다 금지할 태도와 기본 원칙을 고정하는 편이 낫다. 해결책, 판단, 비교, 조롱, 비꼼, 감정 축소를 피하고 짧게 곁에 머무는 답장을 기본형으로 삼는다.

## 결정 5: 차단 범위에 커뮤니티 안전 경계를 포함한다

차단 대상은 욕설/혐오/조롱/멸시/위협뿐 아니라 갈라치기, 정치 논쟁, 젠더 갈등, 학벌/직업/소득/지역/외모/나이 등 비교 갈등, 개인정보/신상 공개, 홍보/스팸/외부 유도, 종교 갈등, 특정 집단 낙인, 피해자 탓하기, 가스라이팅성 표현, 만남/연락처 유도, 고위험 조언 단정, 불법행위 권유까지 포함한다.

### 근거

온설은 논쟁 커뮤니티나 홍보 채널이 아니라 위로를 주고받는 공간이다. 따라서 개별 상대를 해치는 말뿐 아니라 공간 자체를 논쟁장, 홍보장, 위험 조언장으로 바꾸는 말도 차단해야 한다.

## 결정 6: LLM은 OpenAI로 시작하고, EC2에 로컬 LLM을 올리지 않는다

v1 provider는 OpenAI로 한다. 1차 hard safety는 OpenAI Moderation API, 온설식 문맥 판정과 suggestions 생성은 `gpt-5-mini`를 사용한다. 비용 절감 실험 후보로 classifier에 한해 `gpt-5-nano`를 나중에 비교할 수 있다.

EC2 `t3.micro` 서버에는 Ollama 또는 유사한 로컬 LLM 추론 서버를 올리지 않는다. 개인 PC의 Ollama 실험은 가능하지만 v1 운영 범위가 아니다.

### 근거

현재 운영 구조는 Vercel 웹 프론트와 EC2 백엔드 API 서버이며, Terraform 기본 EC2 사양은 `t3.micro`다. GPU가 없고 CPU/메모리도 작으므로 LLM 추론을 같은 서버에 얹으면 API 서버 안정성이 흔들릴 가능성이 크다. 초기에는 EC2 API 서버가 외부 LLM API를 호출하는 구조가 현실적이다.

## 결정 7: LLM 실패 시 자동 허용하지 않는다

classifier 타임아웃 권장값은 3초, rewrite 타임아웃 권장값은 5초로 둔다. classifier 실패/타임아웃은 `uncertain`을 반환하고, rewrite 실패/타임아웃은 `suggestions: []`를 반환한다. 실패 시 자동 `allow`하지 않는다.

### 근거

moderation은 사용자 입력 등록 경로에 있으므로 지연시간을 제한해야 하지만, LLM 실패를 자동 허용으로 처리하면 안전 계층이 장애 시 사라진다. 애매하거나 실패한 경우에는 차단보다 `uncertain` 또는 다시쓰기 계열로 다루는 것이 온설의 안전 기준에 맞다.

## 결정 8: k6/loadtest/seed/system 데이터는 학습·평가·통계에서 제외한다

k6 부하테스트, seed 데이터, 시스템 생성 데이터는 moderation 학습 데이터와 운영 품질 지표에서 제외한다. 백엔드가 `x-load-test-bypass` 헤더, `loadtest-` 접두사, `[load-test:*]` 본문 패턴 등을 감지해 moderation 엔진에 metadata로 넘길 수 있게 한다.

부하테스트 중에는 LLM classifier/rewrite 호출을 생략할 수 있어야 한다.

### 근거

부하테스트 데이터가 학습/평가 데이터에 섞이면 온설의 실제 사용자 언어 기준이 오염된다. 또한 k6 테스트 중 외부 LLM 호출이 섞이면 비용이 튀고, API/DB 성능 측정이 LLM 지연시간에 의해 왜곡된다.

## 산출물

- 요구사항 문서: `docs/superpowers/specs/2026-09-05-onseol-reply-moderation-requirements.md`
- 합의된 결과 타입: `ModerationResult`
- 합의된 판정 action: `allow`, `suggest_rewrite`, `block`, `uncertain`
- 합의된 리라이트 스타일: 짧고 담백한 비해결형 공감
- 합의된 provider: OpenAI Moderation API + `gpt-5-mini`
- 합의된 범위 제외: API 연결, 프론트 UI, DB 변경, 인프라 변경, 로컬 LLM 운영

## 검증

이번 작업은 요구사항과 결정 기록 작성만 수행했다. 코드, API, DB, 프론트엔드, 인프라를 변경하지 않았으므로 lint/typecheck/test 또는 로컬 서버 curl 검증은 실행하지 않았다.

## 남은 일

- 요구사항을 바탕으로 moderation 내부 구현 계획을 작성한다.
- 실제 구현에서 `reply-content-moderation` 서비스/타입/정책/fixture를 추가한다.
- 별도 작업에서 `RepliesService.create()`와 API/UI 연결 여부를 결정한다.
- 운영 로그와 학습 데이터 저장 정책은 DB 변경이 필요한 시점에 별도 결정한다.
