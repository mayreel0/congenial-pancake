# 2026-09-04 — 부하테스트 스코프 결정

## 배경

이메일 인증 프론트엔드(PR #91) 재개를 논의하던 중, 사용자가 부하테스트/
페이크 데이터 시딩을 먼저 하는 게 나을지 물으면서 시작된 라운드. 결론:
부하테스트 픽스처는 회원가입/이메일 경로를 애초에 안 태우도록 설계하면
이메일 인증 유무와 무관하게 항상 재현 가능하다 — 그래서 순서 고민 자체가
불필요해짐. `load-test/`를 정식 도구로 저장소에 남기기로 함(한 번 쓰고
버리는 스크립트가 아니라, 스키마/인증 방식이 바뀌어도 계속 재사용).

## 대상 환경: 로컬, 프로덕션은 나중에 별도 스택으로

실제 `api.onseol.com`(EC2 t3.micro / RDS db.t4g.micro, 버스터블 크레딧
기반)에 직접 부하를 걸면 크레딧 소진으로 실제 서비스가 느려지거나 죽을
위험이 있어 배제. 로컬에서 코드/DB 로직을 검증하고, 실제 캐파가 필요해지면
`infra/terraform`으로 같은 스펙의 임시 스택을 하나 더 띄워서 쓰고 지우는
방식을 쓰기로 함(아직 실행하지 않음, 필요해지면).

## 툴: k6

k6/Artillery/Locust 모두 CLI 자체는 무료 오픈소스 — 유료 요금제는 분산
실행/대시보드를 대신 해주는 클라우드 부가 서비스일 뿐, 이 규모에선
불필요. k6를 선택한 이유: 이 저장소가 전부 TS/JS 스택이라 시나리오
스크립트도 JS로 자연스럽게 맞고, 쿠키/세션 다루기가 편함. 네이티브 앱이나
JWT로 인증 방식이 바뀌어도 k6 자체는 그대로 — API 레이어만 때리는
툴이라 클라이언트 종류/인증 방식과 무관.

## 시나리오 5개

사용자가 처음 제시한 2개(로그인 유저 대량 요청 / 비로그인 유저 IP·쿠키
우회)를 코드 확인 후 아래처럼 정리:

1. 로그인 유저 대량 read/write — 캐파
2. IP 회전 → `ThrottlerGuard`(전역 100/60s, auth 5/60s) 실제 작동 확인 — 정합성
3. guest_id 쿠키 회전 → `settings.guestReplyLimit` 우회 확인 — 정합성/어뷰징
4. 비로그인 읽기 트래픽(가장 흔한 실제 패턴) — 캐파
5. 답변 큐 동시성(좁은 풀에 레이스) — 정합성, PR #73 큐 랭킹 버그 전례 때문에 별도 시나리오로 분리

②③⑤는 "로직이 안 뚫리나"를 보는 정합성 테스트이고, ①④는 "얼마나 버틸
수 있나"를 보는 캐파 테스트 — 사용자가 원래 생각한 "버틸 수 있나"는
①④에 해당, 나머지는 별도 목적.

## 픽스처: 회원가입/로그인/게스트-쿠키-발급 전부 우회

- 세션이 JWT가 아니라 DB row(`sessions` 테이블)이고, `SessionGuard`가
  쿠키뿐 아니라 `Authorization: Bearer` 헤더도 받아준다(모바일 대비로
  이미 있던 경로) — `load-test/seed.ts`가 `users`/`sessions`에 직접
  insert하고 그 토큰을 k6가 Bearer로 씀. `/auth/login`을 한 번도 안
  태우므로 이메일 인증이 나중에 붙어도, 세션이 JWT로 바뀌어도(그땐
  seed.ts가 DB insert 대신 JWT를 직접 sign하도록만 바뀌면 됨) 그대로
  작동.
- `guest_id`는 서버가 DB 검증 없이 그냥 믿는 쿠키라서 k6가 임의 문자열을
  쿠키로 보내기만 하면 새 게스트가 즉석에서 만들어짐 — 발급 절차 자체가
  없음.
- 모든 픽스처(이메일 로컬파트, guest_id)를 `loadtest-` 접두사로 태깅해서
  `--cleanup` 한 번에 다 지울 수 있게 함. 시나리오가 실행 중에 만드는
  guest_id도 반드시 이 접두사를 유지.

## 로컬 실행 중 실제로 발견/수정한 것들

계획만 세우고 끝낸 게 아니라 k6로 실제 로컬 실행까지 해서 검증함 —
그 과정에서 코드 리뷰만으로는 안 보였을 문제 3개를 발견:

1. **스테일 서버 프로세스**: 로컬 8080 포트를 점유하던 프로세스가
   이전(AWS Docker 빌드 검증) 세션에서 안 죽이고 남겨둔 `dist/src/main`
   컴파일 산출물이었음 — landing 모듈이 없던 시점에 빌드된 거라
   `/public/stats`가 404. `nest start --watch` 좀비 프로세스 2개도 같이
   발견. 전부 정리하고 최신 소스로 재기동해서 해결.
2. **스로틀 시나리오 자체의 설계 결함**: `ip-throttle.js`가 처음엔
   `constant-vus` + sleep 없는 루프였는데, 실제 로컬 실행해보니 10 VU로
   초당 ~14,500 요청이 나감 — 필요 이상으로 로컬 서버를 두들기는
   설계였음. `constant-arrival-rate`로 초당 2~5건으로 고정.
3. **①④가 스로틀에 막혀 캐파를 못 잼**: k6 VU가 몇 개든 전부 로컬 머신
   하나의 실제 IP를 공유하므로, 전역 `ThrottlerGuard`(IP당 100/60s)가
   그 IP 전체를 100/60s로 캡함 — 150 VU를 띄워도 그냥 100/60s 밖에 못
   나가고 나머지는 다 429. 즉 ①④가 사실상 ②를 다시 테스트하고 있었던
   것. 사용자에게 옵션 제시(부하테스트 전용 우회 추가 / IP당 한도를
   그대로 인정 / 나중에 분산 러너로) → **부하테스트 전용 우회 추가**로
   결정.

### 부하테스트 전용 스로틀 우회

`apps/api-server/src/app.module.ts`의 `ThrottlerModule.forRoot`에
`skipIf` 추가 — 이중으로 게이팅:
- `NODE_ENV === 'production'`이면 절대 우회 안 됨(하드코딩, 값과 무관)
- `NODE_ENV`가 production이 아니어도, `LOAD_TEST_BYPASS_TOKEN` 환경변수가
  실제로 설정돼 있고(기본값 빈 문자열 — `.env.example`도 빈 값) 요청
  헤더 `x-load-test-bypass`가 그 값과 정확히 일치할 때만 우회.

즉 `NODE_ENV=development`만으로는 절대 우회되지 않고, 운영자가 로컬
`.env`에 토큰을 직접 채워넣어야만 동작 — 실수로 프로덕션에 배포돼도
`NODE_ENV`가 production인 이상 무조건 무시됨(이중 방어).

로컬에서 실측: 우회 없이 150 req/60s 시도 → 95개 성공/55개 429. 우회
헤더 적용 후 동일 시도 → 150개 전부 200. `logged-in-read-write.js`/
`anonymous-read.js` 재실행 결과, 100% 통과, p95 지연시간 각각 97.5ms/
54.3ms(로컬 개발 모드, 프로덕션 빌드 아님) — 150 동시 VU까지 무리 없이
처리.

## 검증한 것 (전부 실제 로컬 실행 기반, 코드 리뷰만이 아님)

- `guest-reply-abuse.js`: 로컬 DB의 실제 `guestReplyLimit`이 스키마
  기본값(5)이 아니라 7로 튜닝돼 있었음 — `GUEST_REPLY_LIMIT` 오버라이드로
  재실행해서 정상 통과 확인(7번째까지 성공, 8번째 409, guest_id 교체 시
  다시 201). 이건 앱 버그가 아니라 로컬 설정값 차이였음.
- `queue-concurrency.js`: 20 VU가 좁은 풀(15개)을 동시에 경합 — 5xx 0건,
  일부 409(레이스에서 짐, 정상)만 발생.
- `ip-throttle.js`: 429가 실제로 트리거되는지가 성공 조건 — 511개 요청 중
  356개가 429, 두 예산(전역 100/60s, auth 5/60s) 모두 작동 확인.
