# 온설 회원탈퇴 결정 기록

## 배경

OAuth "연동 해제" 기능을 다음 라운드로 검토하다가, 정작 그 기능이 왜 필요한지 확실한 이유가 없다는 걸 확인(사용자: "나한테 물어봐도 내가 제시한 기능도 아니라서 나도 모르지") — 이전 세션이 코드 주석("연동 해제는 의도적으로 범위 밖")만 보고 백로그에 넣은 것으로 드러났다. 대신 사용자가 "그보다는 차라리 서비스에 회원탈퇴가 필요하지않아?"라고 제안 — 실제로 코드 전체를 확인한 결과 회원탈퇴 기능이 전혀 없었다.

## 결정 1: 스코프를 계정/개인정보 삭제로 한정 — 접속 로그 보관, 부정이용 방지 해시는 별도 백로그로 분리

사용자가 개인정보보호법 관련 자료를 직접 조사해 공유(통신비밀보호법상 접속 로그 3개월 보관 의무, 개인 식별 정보 즉시 파기 원칙, 부정이용 방지용 해시 보관 관행 등). 이 프로젝트가 실제로 무엇을 저장하는지 확인한 결과:

- **접속 로그(IP 등)는 애초에 DB에 저장하지 않음** — `sessions` 테이블에 `user_agent` 컬럼만 있고 어디서도 안 읽힘, `main.ts`의 IP 관련 코드는 rate-limit 판단에만 순간적으로 쓰고 저장 안 함. 이 요건이 실제로 적용된다면 애플리케이션이 아니라 ALB/웹서버 로그 같은 인프라 계층의 문제이고, 탈퇴 여부와 무관하게 모든 트래픽에 적용되는 것이라 이번 라운드 스코프 밖으로 분리.
- **부정 이용 방지용 해시 보관**도 지금 온설엔 계정 단위 영구 차단 메커니즘 자체가 없어서(어뷰징 방지는 전부 게스트 쿠키 기반) 지금 만들어봐야 검사할 곳이 없는 죽은 데이터 — 나중에 계정 단위 제재 기능이 생기면 그때 같이 고려하기로 함.

이번 라운드는 순수하게 "계정 개인정보(이메일/닉네임/비밀번호/OAuth 연동)를 어떻게 파기하는가"에 집중.

## 결정 2: 콘텐츠는 남기고 계정만 익명화 — 작성자 연결을 끊는 게 아니라 사용자 행 자체를 스크럽

사용자 결정: "작성자 연결만 끊고 콘텐츠는 남김. 나만의 컨텐츠가 아니라 서로의 컨텐츠이니까."

`requests`/`replies` 테이블엔 `CHECK (author_id IS NOT NULL OR guest_id IS NOT NULL)` 제약이 있어서 탈퇴한다고 `author_id`를 null로 만들 수 없다. 대신 `users` 행 자체를 스크럽하는 방식을 택했다 — `toAuthorDisplayDto`(`apps/api-server/src/common/author-display.ts`)가 이미 "닉네임을 공개했는데 그 사이 닉네임이 없어졌으면 익명으로 폴백"하는 로직을 갖고 있어서(기존에 존재하던 로직, 이번에 새로 만들지 않음), `users.nickname`을 null로 만들기만 하면 과거에 공개했던 글들도 자동으로 익명 처리된다. `email`은 `NOT NULL UNIQUE`라 null 대신 `deleted-<id>@deleted.invalid`로 치환해 제약을 유지하면서 원래 이메일을 재사용 가능하게 풀어준다.

## 결정 3: 유예기간(기본) + 즉시삭제(옵션), 둘 다 제공 — 사용자 결정 그대로

> "복구 가능성과 즉시삭제 모두 열어두고 확인 절차와 유예기간을 두는게 낫다고 생각함."

- 기본: 탈퇴 요청 시 세션 전부 무효화 + 즉시 로그아웃, `deletionRequestedAt`만 기록 — 이메일/닉네임/비밀번호/OAuth 연동은 그대로 둠.
- `immediate: true` 옵션: 그 자리에서 바로 스크럽(위 결정 2와 동일 로직) — 복구 불가.
- 유예기간(30일) 동안 재로그인하면 계정이 여전히 정상 조회되고(`GET /auth/me`가 `deletionGracePeriodEndsAt`을 내려줌), 프론트엔드가 이 값을 보고 복구/로그아웃 다이얼로그를 띄운다. 사용자 결정: "로그인 시 자동복구 말고 회원 탈퇴 신청중인 유저라는걸 알려주는 복구 다이얼로그를 보여줬으면 해. 남은 기간도 알려주고." — 자동 복구가 아니라 명시적 확인을 요구하는 것으로 확정.
- 유예기간이 지나면 매일 도는 cron(`AccountDeletionCronService`, `@nestjs/schedule` 신규 추가)이 같은 스크럽 로직으로 자동 확정 삭제.

## 결정 4: 재로그인 시 자동 복구가 아니라 명시적 다이얼로그

처음엔 "유예기간 중 로그인하면 자동으로 복구"를 제안했으나 사용자가 명시적 확인 절차를 요청. 최종 설계는 로그인/OAuth 로직을 전혀 건드리지 않고, 이미 있는 세션 상태 확인 패턴을 재사용한다 — 로그인은 유예기간 중이어도 평소처럼 성공하고, `GET /auth/me` 응답의 `deletionGracePeriodEndsAt` 필드 하나로 프론트엔드가 어느 페이지에 있든 복구 다이얼로그를 띄운다(루트 레이아웃에 전역 마운트). "복구하기"는 이미 있는 세션만으로 처리(`POST /auth/restore-account`, 재인증 불필요), "로그아웃"은 그냥 로그아웃 — 배경 클릭으로는 닫히지 않게 만들어 실수로 로그아웃되는 걸 방지(기존 `ui/ActionConfirmDialog`는 배경 클릭이 곧 취소라 이 용도엔 안 맞아 별도 컴포넌트로 구현).

## 검증

- **실제 로컬 DB + 실행 중인 서버**에 대해 curl로 전체 시나리오 검증(단위 테스트로 각 서비스 메서드도 별도 검증됨):
  - 유예기간 탈퇴 → 세션 즉시 무효화(같은 토큰으로 이후 `/auth/me` 401) → 이메일/닉네임/비밀번호 원본 유지, `deletion_requested_at`만 기록됨을 DB에서 직접 확인.
  - 새 세션으로 `/auth/me` 호출 → `deletionGracePeriodEndsAt`이 정확히 요청 시각+30일로 계산됨을 확인.
  - `/auth/restore-account` 호출 → `deletion_requested_at`이 null로 복구됨을 DB에서 확인.
  - `immediate: true` 탈퇴 → 이메일이 `deleted-<id>@deleted.invalid`로 치환, 닉네임/비밀번호 null, `oauth_identities` 행 삭제, `deleted_at` 기록을 DB에서 확인. 사전에 만들어둔 공개 글(`anonymous: false`)의 행 자체와 `author_id`는 그대로 남아있음을 확인(CHECK 제약 위반 없음).
  - 스크럽 후 같은 원본 이메일로 재가입 요청 시 "이메일 중복" 에러가 아니라 정상적으로 다음 단계(실제 메일 발송 시도, 로컬 환경이라 502)까지 진행됨을 확인 — 원본 이메일이 실제로 재사용 가능해졌음을 증명.
- `pnpm run verify`(전체 워크스페이스 lint/typecheck/test/build) 통과.
- `@nestjs/schedule`이 ESM 전용 패키지라 Jest 기본 설정으로는 테스트 시 파싱 실패 — 실제 프로덕션 Node 24.14.0 런타임에서는 `require()`가 문제없이 동작함을 직접 확인(Node 22+의 동기 ESM require 지원)한 뒤, `transformIgnorePatterns`를 조정해 Jest에서도 이 패키지를 변환하도록 수정.

## 남은 일

- 접속 로그 3개월 보관(통신비밀보호법) — 실제로 적용 대상인지, 적용된다면 인프라 계층(ALB 액세스 로그 등)에 어떻게 반영할지는 별도 라운드.
- 부정 이용 방지용 해시 보관 — 계정 단위 제재 메커니즘이 생기기 전까진 보류.
- `apps/admin`에서 탈퇴/유예기간 중 계정을 조회·강제 확정하는 관리 기능은 이번 라운드에 없음(필요성 확인되면 별도 라운드).
