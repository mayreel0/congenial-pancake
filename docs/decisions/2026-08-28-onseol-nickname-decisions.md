# 온설 고정닉네임 결정 기록

## 배경

이전 라운드(OAuth 계정 비밀번호 부여)에서 "온설이 계속 익명 전용이어야 하는가"라는 고민이 다시 나왔었다 — "익명 커뮤니티도 열심히 활동함을 티내고 싶은 사람들이 있다"는 관찰과, "무조건 익명으로만 하면 재미가 떨어진다"는 사용자 본인의 반성이 맞물려, 이번 라운드에서 실제로 진행하기로 확정했다.

## 결정 1: 게시물당 선택 — 계정 단위 스위치 아님

닉네임 공개 범위를 "게시물 작성/답장할 때마다 익명/닉네임 중 선택"으로 확정(사용자 선택). 계정 단위로 한 번 켜면 그 이후 전부 닉네임으로 나가는 방식은 기각 — 한 번이라도 닉네임을 켜면 과거 게시물까지 전부 연결되어버리는 게 아니라, 매 글마다 독립적으로 익명 여부를 선택할 수 있어야 "필요할 때만 티내고, 나머지는 여전히 완전히 익명"이 가능하다는 점이 결정적이었다. 이번 라운드는 닉네임 저장/설정까지만 다루고, 실제 게시물 작성 시 선택하는 UI/API는 범위 밖(다음 라운드).

## 결정 2: 닉네임은 유니크하지 않되, 구분 가능한 수단은 필요

"중복이 가능하더라도 구분이 가능한 수단은 있어야함" — 유니크 제약을 걸지 않으면서도(아이디 헌팅 같은 가입 마찰 없이) 같은 닉네임을 쓰는 두 사람을 구분할 방법이 필요하다는 요구. Discord식 discriminator 패턴 채택: `users.id`(UUID)에서 대시를 뺀 마지막 4자리 hex를 대문자로 변환해 붙임(`민들레#C376`). 별도 컬럼/DB 조회 없이 결정적으로 계산 가능하고, 유니크 제약이 주는 부담(탈락한 이름 재사용 불가, 선점 경쟁) 없이 목적을 달성한다.

## 결정 3: 공개 프로필 페이지는 이번 라운드 범위 밖

"이번 라운드에 공개 프로필 페이지도 포함할까요?" 질문에 "아니요, 닉네임만 먼저"로 확정 — 프로필 페이지는 신고/차단 등 별도 설계가 필요한 더 큰 범위라 판단해 명시적으로 분리.

## 산출물 (이번 라운드: 닉네임 저장/설정만)

- `apps/api-server`: `users.nickname`(nullable text, 유니크 아님) 컬럼 추가.
- `src/users/nickname-discriminator.ts` — `nicknameDiscriminator(userId)` 순수 함수, 단위 테스트 포함.
- `POST /auth/nickname`(세션 필요) — 닉네임 설정/변경. `UpdateNicknameDto`: 1~20자, 공백만으로는 불가.
- `UserResponseDto`에 `nickname`/`nicknameDiscriminator` 필드 추가 — `/auth/me`, 로그인/가입 응답에서도 항상 함께 내려옴(닉네임 미설정이어도 discriminator는 항상 계산되어 내려감 — 프론트가 나중에 닉네임을 설정하는 순간 바로 쓸 수 있도록).
- 아직 아무 곳에도 "공개"되지 않음 — `requests`/`replies` 작성 시 닉네임을 쓸지 선택하는 기능, 응답에 닉네임을 노출하는 기능은 전부 다음 라운드.

## 검증

- `apps/api-server`: lint/typecheck/test(60/60, discriminator 단위테스트 3개 포함)/build 통과. 마이그레이션 실제 적용.
- curl로 실사용 검증: 회원가입 → 닉네임 설정("민들레") → `/auth/me`에 정확히 반영 확인. 검증 실패 케이스(빈 문자열/공백만/21자) 전부 400 확인, 세션 없이 호출 시 401 확인. **핵심 요구사항 실측**: 두 번째 계정으로 같은 닉네임("민들레")을 설정해도 정상 허용되고, 두 계정의 discriminator가 서로 다르게(`4CD8` vs `AD0D`) 나오는 것 확인 — "중복 허용 + 구분 가능" 요구를 정확히 만족.
