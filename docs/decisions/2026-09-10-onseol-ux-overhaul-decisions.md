## 결정: 버튼 pending 스피너는 지연 노출 없이 즉시 떠야 한다

처음엔 "빠른 요청에서 깜빡이지 않게" 스피너를 ~200ms 지연 노출하는 `useDelayedPending` 훅을 시도했으나, 로그인 버튼에 실제 적용해 사용자가 직접 테스트한 뒤 강하게 반려: "저게 지연노출이라고? 엉망인데? ... 눌렀는데 갑자기 비활성화가 되고 이후에 스피너가 돈다는 상상을 해본적도 없다." 버튼이 비활성화됐는데 스피너가 아직 안 뜨는 구간이 "먹통"처럼 느껴진다는 지적. 전면 되돌림(PR #177 내 커밋으로 리버트).

이후 완전히 지연 없이 즉시 노출하는 것도 시도했으나 반대 문제 발생 — 로컬에서 매우 빠른 요청(닉네임 저장 등)은 스피너가 한 프레임도 안 되게 스쳐 지나가 "아무 반응 없음"처럼 느껴짐. 사용자 본인의 표현: 순수 UI 변경은 즉시가 맞지만, 실제 생성/수정/삭제는 0.몇 초 스피너가 보이는 게 오히려 "서버가 느리다"는 인상을 안 줌. 최종 설계는 `useMinDisplayDuration`을 재사용한 `BUTTON_PENDING_MIN_MS`(프로덕션 300ms/테스트 0ms) — **등장은 즉시(같은 렌더에서 disabled와 spinner가 함께 뜸), 사라짐만 최소 시간 유지**. 13개 호출 지점에 동일 적용, `disabled`와 `pending`이 항상 같은 계산값을 쓰도록 해서 상태 불일치 창을 없앰. 실측(MutationObserver 기반)으로 클릭 후 약 29ms만에 disabled+spinner가 함께 뜨는 것까지 확인됨.
