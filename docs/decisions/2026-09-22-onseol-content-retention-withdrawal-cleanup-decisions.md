# 온설 삭제 콘텐츠 보존 기간 + 탈퇴 시 정리 결정 기록

## 배경

개인정보처리방침을 준비하며 코드를 실제로 조사하다가, 문서에 "사실과 다른 내용"을 쓰게 될 뻔한 지점 두 개를 발견했다.

1. **"삭제하기"가 실제로 본문을 지우지 않음**: 본인이 삭제한 글/답장(`contentRemoved`/`deletedAt`)은 화면에서만 placeholder로 가려질 뿐, DB에는 원문이 영구히 남아 있었다(관리자가 신고를 검토하려면 원문이 필요하다는 이유로 일부러 남긴 설계 — [[own-content-deletion 결정]] 참고). 이를 지우는 뒷정리 배치가 없었다.
2. **탈퇴해도 푸시 구독이 안 지워짐**: 세션·이메일·닉네임·소셜 연동은 탈퇴 시 정리되는데 푸시 구독은 빠져 있어서, 탈퇴한 계정의 옛 글에 나중에 답장이 달리면 그 기기로 알림이 갈 수 있었다.

## 결정: 삭제 후 30일 뒤 자동 파기(즉시 파기도, 무기한 보관도 아님)

정책 초안에 "삭제 후 30일 뒤 파기"라고 쓰기로 확정하고, 그에 맞춰 코드를 먼저 구현. 즉시 파기는 신고 검토·분쟁 대응 여지를 없애고, 무기한 보관은 "삭제"라는 말과 맞지 않는다는 절충.

## 구현(PR #271)

- **콘텐츠 파기**: 매일 05:00에 도는 `ContentRetentionCronService`가 본인 삭제(`content_removed_at` 기준)/운영자 영구 삭제(`deleted_at`)한 요청, 삭제된 답장(`deleted_at`)의 본문을 `''`로 비움. 행 자체는 남겨서 스레드 구조와 다른 사람의 답장은 그대로 유지. 답장에서 파생된 검토 로그의 수정 제안(`suggestions`)도 함께 비움.
- `requests.content_removed_at` 컬럼 신설, 마이그레이션에서 이미 삭제된 기존 글은 배포 시점부터 30일로 기산하도록 백필.
- **탈퇴 정리**: 탈퇴 요청 시(즉시/유예 모두) 푸시 구독 삭제, 탈퇴 확정 시 알림 내역 삭제.

## 리뷰에서 찾은 실제 버그 2건

- `finalizeAccountDeletion`(탈퇴 확정 경로)에는 푸시 구독 삭제가 빠져 있었음 — 이 PR 배포 전에 이미 탈퇴 유예 중이던 계정은 `requestWithdrawal`을 다시 거치지 않고 확정되므로 구독이 영구히 남을 뻔했음. 확정 경로에도 멱등하게 추가.
- 검토 로그 갱신을 `inArray`로 한 번에 처리하면 대량 파기 시(예: 마이그레이션 백필 30일 경과 시점) Postgres 바인드 파라미터 한도를 넘을 수 있어 1000개씩 청크로 나눠 처리하도록 수정.

## 검증

- 유닛테스트 통과 + **실제 로컬 DB에 테스트 행을 넣고 진짜 저장소 코드로 파기를 실행**: 40일 전 삭제분만 본문이 비워지고 5일 전 삭제분/정상 글은 그대로임을 확인, 재실행 시 0건(멱등성), 대량 처리 청크 분할 테스트 추가. 테스트 행은 정리해서 삭제.
- 마이그레이션 백필 후 "삭제됐는데 파기 시각이 비어있는 행" 0건 확인.

## 남은 일

- 30일 값(`REMOVED_CONTENT_RETENTION_DAYS`)은 개인정보처리방침에도 같은 값으로 게시해야 함 — 바꾸면 문서도 같이 바꿔야 함.
- `UsersRepository`가 `push_subscriptions`/`notifications` 테이블을 직접 다루는 건 `NotificationsModule`↔`AuthModule` 순환 의존을 피하려는 임시 우회 — 탈퇴 정리 로직이 더 늘어나면 전용 서비스로 분리하는 걸 고려.
- `deleted_at`/`content_removed_at`에 인덱스는 아직 없음 — 지금 규모(수천 행)에서는 순차 스캔 비용이 무시할 수준이라 보류, 데이터가 커지면 부분 인덱스 추가 검토.
