# 온설 admin 앱 구조 결정 기록

> 메모리 요약([[admin_app_and_module]], [[admin_app_architecture_backlog]])과 PR 기록을 대조해 재구성.

## 배경

`/admin`은 `apps/web`과 별도 앱(`apps/admin`, 별도 포트)으로 분리돼 있고, `apps/web`의 로그인 세션 쿠키를 그대로 공유한다(별도 JWT 발급 없음).

## 결정 1: 로그인 라우트를 admin 앱 안으로 분리 (PR #179)

기존에는 admin 접근 시 web 앱의 로그인 화면으로 리다이렉트하는 방식이었는데, admin 전용 로그인 라우트를 admin 앱 자체에 두는 구조로 변경. 공유 세션 쿠키 메커니즘 자체는 그대로 유지 — 로그인 UI 위치만 옮긴 것.

## 결정 2: OAuth 전용 계정의 admin 로그인 처리는 "버그"가 아니라 "안내 문구 누락"이었다

소셜 로그인만으로 가입한 계정이 admin에 로그인할 때 헷갈리는 문제가 제기됐으나, 조사 결과 공유 쿠키 메커니즘 자체는 이미 정상 동작 중이었고 실제 문제는 안내 문구 부재였음. 별도 로그인 플로우를 새로 만드는 대신 안내 텍스트만 추가해 해결(2026-09-08).

## 결정 3: AdminNav 모바일 대응 — 햄버거 메뉴 + 접이식 사이드바 (PR #188/#190)

admin 앱 자체가 모바일 폭 대응이 안 돼 있던 것을 별도 라운드로 정리. 사이드바를 접었다 펼 수 있게 하면서, 이후(PR #252) 필터 영역 반응형 작업에서 "사이드바 접힘에 따라 사용 가능 너비가 뷰포트와 달라진다"는 제약의 원인이 됨 — 뷰포트 breakpoint 대신 컨테이너 쿼리를 쓰게 된 배경([[container_query_filter_row_fix]] 참고, 별도 문서 `2026-09-17-onseol-notifications-delete-and-filter-responsive-decisions.md`에 정리).

## 결정 4: NestJS 컨트롤러 등록 순서가 실제 라우팅에 영향

admin 관련 API를 늘리는 과정에서, `@Module({ controllers: [...] })` 배열의 순서가 실제 라우트 매칭 순서를 결정한다는 걸 확인 — `:id` 같은 와일드카드 경로를 가진 컨트롤러가 리터럴 경로 컨트롤러보다 먼저 등록되면 리터럴 경로가 와일드카드에 먼저 잡혀버림. 유닛 테스트로는 이 문제를 못 잡고, 실제 라우팅 확인이 필요했음. 이후 admin 쪽에 컨트롤러를 추가할 때마다(#229/#230/#232/#236 등) 등록 순서를 의식적으로 검토하는 계기가 됨.

## 검증

- 각 PR typecheck/lint/knip/유닛테스트 통과.
- 모바일 사이드바는 실제 좁은 뷰포트에서 동작 확인.
- 컨트롤러 순서 문제는 실제 HTTP 요청으로 라우팅 결과를 확인해서 발견.
