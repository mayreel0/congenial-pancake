# 온설 검색 기능(내 글 검색) 결정 기록

## 배경

남은 백로그를 점검하는 과정에서 시작. PR #205(OG 이미지)는 시각 디자인 판단이 필요해 사용자가 직접 맡기로 했고 손대지 않기로 확정([[visual_design_prs_stay_manual]] 참고). 다음으로 검색 기능을 넣기로 했는데, 어디에 어떤 범위로 넣을지가 쟁점이었다.

## 결정: 전체 피드(`/read`) 검색이 아니라 `/records`의 "내 글 검색"만 제공

`/read`는 익명 게시물이 하루 단위로 흘러가는 공개 피드다. 여기에 키워드 검색을 붙이면 "누가 어떤 단어를 썼는지"로 거슬러 올라가는 재식별(re-identification) 경로가 생긴다 — 이 서비스의 핵심 설계(닉네임 비공개 기본, `authorId`/`guestId`가 API를 절대 넘지 않는 것 등)와 정면으로 충돌한다. 그래서 전체 피드 검색은 **의도적으로 제외**하고, 로그인한 본인만 볼 수 있는 `/records`("내 기록")에서 자기 글만 검색하는 기능으로 범위를 좁혔다.

## 구현

- **백엔드(PR #249)**: `GET /requests/mine?q=`, `GET /replies/mine?q=` — 본문(body)에 대한 `ILIKE` 검색. 본인 소유 목록에만 적용되므로 접근 제어는 기존 `findMine`류 쿼리와 동일.
- **프론트엔드(PR #250)**: `MyRequestLogSection`/`MyAnswerLogSection`에 검색창 추가, 기존 `useDateRangePage`류 URL 상태 패턴(`?q=`)을 그대로 확장. 입력 중 매 타이핑마다 요청을 보내지 않도록 디바운스 처리.

## 검증

- `pnpm --filter api-server test`/`pnpm --filter web test` 통과.
- 로컬 서버에서 실제 검색어로 본인 글/답변 목록이 좁혀지는지, 날짜 범위 필터와 검색어가 함께 걸리는지 확인.
