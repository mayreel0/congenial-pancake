# 온설 본인 글/답장 삭제 결정 기록

## 배경

회원탈퇴 기능(PR #161/#162) 이후 다음 라운드로 "본인 글/답장 삭제 기능"을 선택. 논의 중 사용자가 핵심 쟁점을 제기: "그러면 내가 남긴 글을 삭제했을때 남들은 볼 수 있게 되는거야? 만약에 남들도 보기 싫을정도로 부끄러운 글을 작성했다 생각해서 지우고 싶다 이게 그 복잡한 내용인데" — 단순히 숨기는 걸로는 부족하고, 삭제한 사람의 의도(부끄러운 글을 남들이 못 보게)를 실제로 보장해야 한다는 문제.

## 결정 1: 기존 `hidden`/`deletedAt`을 재사용하지 않고 별도의 `contentRemoved` 플래그를 신설

`requests`/`replies`의 기존 `hidden`(관리자 신고 자동 숨김)/`deletedAt`(관리자 영구 삭제)은 피드 조회 쿼리(`findFeed`/`findVisible` 등)에서 요청(request) 최상위 레벨로 걸러진다 — 즉 요청 자체가 hidden/deletedAt이면 그 밑에 달린 답변(reply)까지 통째로 안 보이게 된다. 본인 글 삭제는 "내 글은 숨기되 남들이 남긴 답변은 그대로 유지"해야 하므로 이 매커니즘을 그대로 쓰면 답변까지 사라지는 부작용이 생긴다. 그래서 `requests`에 `contentRemoved`라는 완전히 별개의 boolean 컬럼을 추가하고, 본문 노출 여부만 이 플래그로 따로 제어한다. 답변(reply) 삭제는 이런 캐스케이드 문제가 없어서 기존 `deletedAt` soft-delete를 그대로 재사용.

## 결정 2: 삭제된 원문은 예외 없이 항상 placeholder로 대체 — 삭제한 사람 편을 든다

사용자가 직접 반례를 제기: "흠... 내가 답장한 글 원문을 볼 수 없는게 맞나 싶기도 하네" — 즉 자신이 답변을 남긴 요청의 원문을 나중에 그 글쓴이가 삭제했을 때, 답변자 본인의 "내가 남긴 답변" 기록에서도 원문이 사라지는 게 맞는지에 대한 의문. 이에 대해 논의한 끝에 사용자가 확정: "예외 없이 삭제한 사람 편을 들어주는 게 맞다는 말이 맞는것같네." — 즉 조회하는 사람이 누구든(글쓴이 자신의 기록, 답변자의 답변 기록, 공개 프로필 등) 예외 없이 동일한 placeholder("삭제된 글이에요.")로 대체한다.

구현은 `visibleRequestBody()` 헬퍼 하나로 강제 — 요청 본문을 노출하는 모든 지점(피드, 기록, 답변 기록, 공개 프로필)이 원본 `body` 컬럼을 직접 읽지 않고 반드시 이 헬퍼를 거치도록 해서, 예외 지점이 새로 생기지 않게 함.

### 예외: 관리자 신고 검토 화면

관리자 모더레이션 DTO(`admin-request.dto.ts`/`admin-reply.dto.ts`)는 이 규칙에서 제외 — 신고를 검토하려면 실제로 무슨 내용이었는지 봐야 판단이 가능하다는 이유로, 구현 중 임의로 실제 본문을 그대로 노출하도록 남겨두었다가 사후에 사용자에게 확인 요청, 그대로 유지하기로 확정.

## 결정 3: 공개 랜딩 페이지의 무작위 샘플에서는 placeholder 대신 완전히 제외

랜딩 페이지의 "샘플 대화" 기능(`findSampleExchanges`)은 삭제된 글을 placeholder로 보여주면 그 자체로 어색한 UI가 되므로, placeholder 치환이 아니라 샘플 추출 대상에서 아예 제외하도록 WHERE 조건을 추가. 이 부분은 사용자에게 명시적으로 물어보지 않고 판단한 것이나, 결정 2("예외 없이 삭제한 사람 편")의 자연스러운 연장으로 처리.

## 결정 3-1: 답변 삭제도 같은 원칙 적용 — 원글 작성자의 "내가 남긴 고민" 기록에서도 실제로 사라져야 함

프론트엔드 작업 직전 자체 점검 중 발견: `RequestsRepository.findMine`("내가 남긴 고민" 탭이 쓰는 쿼리)은 기존부터(이번 기능 이전부터) 자신이 받은 답변을 hidden/deletedAt 필터링 없이 그대로 보여주는 정책이었다(관리자가 숨긴 답변도 글쓴이 본인에겐 그대로 보이는 기존 동작). 답변 삭제가 기존 `deletedAt` soft-delete를 재사용하는데, 이 정책과 그대로 충돌 — 답변을 삭제해도 그 답변을 받은 원글 작성자 입장에서는 삭제 전 원문이 계속 보여서 삭제 기능이 사실상 무효화되는 문제였다. 사용자에게 확인 후("답변을 삭제하면 ... 요청한 기능과 정면으로 충돌하는데, 이걸 이번 라운드에서 같이 고칠까?" → "같이 고친다") `visibleRequestBody`와 대칭되는 `visibleReplyBody()` 헬퍼를 신설해 `toMyRequestLogEntryDto`의 중첩 답변 목록에 적용. 관리자의 "숨김"(`hidden`, 검토 대기)과는 별개로 "삭제됨"(`deletedAt`, 자진 삭제/관리자 영구삭제 공통 필드)만 placeholder("삭제된 답변이에요.") 대상으로 삼는다.

같은 대칭 원칙을 확장해, 답변 작성자 본인이 자신의 "내가 남긴 답변" 기록에서 자신이 삭제한 답변을 보는 경우(`toMyAnswerLogEntryDto`의 `replyBody`)에도 동일하게 placeholder를 적용 — 요청 삭제 쪽에서 이미 확정된 "예외 없이, 조회하는 사람이 누구든" 원칙(결정 2)을 답변에도 그대로 확장한 것으로, 이 부분은 사용자에게 별도로 재확인하지 않고 기존 확정 원칙의 연장으로 적용했다.

## 결정 4: 스코프를 로그인 회원 본인 콘텐츠로 한정 — 게스트 콘텐츠 삭제는 이번 라운드에 없음

사용자 결정: "응 회원만으로 진행해줘." 게스트(비로그인) 작성 글/답변에 대한 본인 삭제 기능은 이번 라운드에 포함하지 않음.

## 검증

- `pnpm --filter api-server typecheck`/`test`/`lint` 통과(신규 `deleteOwn` 서비스 로직 및 `visibleRequestBody()` 헬퍼 단위 테스트 포함).
- **실제 로컬 DB + 실행 중인 서버**에 대해 curl로 시나리오 검증:
  - 소유자가 아닌 사용자가 `POST /requests/:id/delete-own` 또는 `POST /requests/:id/replies/:id/delete-own` 호출 시 404(존재 여부를 숨기기 위해 "없음"과 "내 것 아님"을 동일하게 처리).
  - 인증 없이 호출 시 401.
  - 실제 소유자가 호출 시 204 및 DB에 `content_removed`/`deleted_at`이 정확히 기록됨을 확인.
  - 삭제한 글쓴이 본인의 `/requests/mine`(기록) 응답에서 원문이 placeholder로 대체됨을 확인.
  - 그 글에 답변을 남긴 사람의 `/replies/mine`(답변 기록) 응답에서도 원문(requestBody)이 placeholder로 대체됨을 확인.
  - `/public/samples`(랜딩 페이지 샘플) 응답에 삭제된 글이 전혀 포함되지 않음을 확인.
- 결정 3-1(답변 삭제 대칭 적용) 관련 유닛 테스트: `visibleReplyBody` 자체(`request-content.spec.ts`), `toMyRequestLogEntryDto`가 삭제된 답변을 placeholder로 대체하는지(`my-request-log-entry.dto.spec.ts`), `toMyAnswerLogEntryDto`가 요청/답변 각각 삭제됐을 때 독립적으로 placeholder를 적용하는지(신규 `my-answer-log-entry.dto.spec.ts`) 모두 통과.

## 프론트엔드: `/records` 삭제 버튼

`RequestLogCard`/`AnswerLogCard`에 각각 본인 소유 항목(내 고민 / 내 답변)에만 `ui/MoreMenu`(기존 `/read`의 "신고하기"와 동일 패턴) → "삭제하기" → `ui/ActionConfirmDialog` 확인 흐름을 추가. 이미 삭제된 항목(`removed`/`replyRemoved: true`)은 메뉴 자체를 숨김 — 재삭제 시도나 혼란을 막기 위해. 프론트엔드가 이 상태를 정확히 판단할 수 있도록 `myRequestLogItemSchema`에 `removed: boolean`, `myAnswerLogEntrySchema`에 `requestRemoved`/`replyRemoved: boolean`을 추가(본문 문자열을 placeholder와 비교하는 방식은 취약해서 피함).

**검증 방식**: 컴포넌트 단위 테스트(`apps/web/app/records/page.test.tsx`, 실제 React 렌더 + 실제 클릭 이벤트로 메뉴 열기 → 삭제 확인 → 실제 fetch 호출 검증, 이미 삭제된 항목엔 메뉴가 안 보이는지까지 포함)로 검증. 실제 크롬 브라우저로도 검증을 시도했으나, 이 세션이 쓰는 크롬 인스턴스가 로컬 개발 서버에 사용자의 실제 계정으로 이미 로그인돼 있어서(가짜 테스트 세션 쿠키 주입이 조용히 실패함 — `/auth/me`로 확인 후 발견) 실제 계정 데이터를 건드릴 위험이 있어 중단, 탭을 닫고 실제 데이터는 전혀 건드리지 않음. 브라우저 시각 확인은 사용자가 직접 로컬 개발 서버에서 확인하는 걸 권장.

## 남은 일

- 위 컴포넌트 테스트로 동작은 검증했지만, 실제 브라우저에서의 시각적 확인은 못 함 — 필요하면 사용자가 직접 `/records`에서 확인.
