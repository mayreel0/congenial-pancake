# 온설 답변 큐/보류/넘기기 결정 - 2026-08-22

`/answer`·`/read`를 실제 API로 연동하는 라운드의 첫 단계(백엔드, answer 쪽만)에서 정한 결정을 기록한다. `docs/decisions/2026-08-21-onseol-db-and-moderation-decisions.md`/`2026-08-21-onseol-anonymous-posting-decisions.md`이 이미 정해둔 신고 3명 임계치·비회원 글쓰기 정책은 그대로 유지하고 손대지 않았다.

## 배경: 답변 큐 랭킹 알고리즘

이전 대화에서 이미 방향을 확정해뒀다(원칙만, 구현은 이번에 처음):

- **신선도 60시간**: 생성된 지 60시간이 지난 요청은 답변 큐에서 완전히 빠진다(`/read`에서는 계속 보임 — 읽기는 신선도 제한이 없다). 오래된 요청에 뒤늦게 답하면 요청한 사람 입장에서 감정이 이미 지나간 경우가 많다는 판단.
- **답장 수 오름차순 + 캡 5**: 요청 하나가 라운드당 답장 5개를 받으면, 다른 대안이 있는 한 큐에서 빠진다. 단, 남은 요청이 전부 캡에 도달했다면 그때는 캡을 무시하고 배분을 계속한다(그렇지 않으면 조용한 시간대에 아무도 답할 게 없어짐).
- **인위적 품질 가중치 없음, 넘기기 횟수도 랭킹에 안 씀**: "좋은 글"을 우선 노출하는 로직은 넣지 않는다(판단 기준이 없음). 넘기기(skip)도 마찬가지로 절대 랭킹에 반영하지 않는다 — 무거운 사연이라 부담스러워서 넘기는 경우와 저품질이라 넘기는 경우를 구분할 방법이 없어서, 넘기기 반영 시 정작 답변이 제일 필요한 글이 묻힐 위험이 있다는 사용자의 판단.

이번 라운드는 이 규칙을 `RequestsRepository.findQueueCandidate()`(요청당 두 번의 쿼리 — 캡 적용 시도 후 결과 없으면 캡 무시하고 재시도)로 실제 구현했다.

## 결정 1: 비회원은 넘기기만, 보류·저장은 로그인 필수

요청/답장 작성과 달리, 넘기기/보류/저장 세 가지를 똑같이 취급하지 않기로 했다.

- **넘기기(skip)**: 비회원도 가능. guestId로 식별.
- **보류(hold)**: 로그인 필수. 비회원이 시도하면 401.
- **저장(save, `/read`용 — 이번 라운드 범위 밖)**: 로그인 필수로 예정.

### 근거

넘기기는 "다시 보여주지 마" 정도의 가벼운, 되돌릴 필요 없는 액션이라 비회원도 문제없다. 보류·저장은 "나중에 돌아올게"라는 약속에 가까운데, guestId는 브라우저 로컬 값이라 언제든 사라질 수 있어 계정만큼 신뢰할 수 없다 — 이 둘은 실제 계정이 있어야 의미가 있다고 판단했다.

넘기기를 비회원까지 허용하면서도 랭킹에 영향이 없어야 한다는 요구사항(위 배경 참고) 때문에, 넘기기는 **철저히 조회자 1명 한정 제외 필터**로만 쓰인다 — 다른 조회자의 큐나 전체 랭킹에는 절대 반영되지 않는다. `answer_interactions` 테이블에 신고처럼 신고자를 집계하는 로직이 없다.

## 결정 2: `answer_interactions` 스키마 — 넘기기/보류를 한 테이블로

`requests`/`replies`/`reports`와 같은 authorId-nullable + guestId 패턴을 따르되, 두 가지를 추가했다.

- `status` enum(`skipped` | `held`) — 조회자 1명당 요청 1개에 대해 최대 한 행. `unique(requestId, authorId)`와 `unique(requestId, guestId)`를 각각 걸어서(둘 다 nullable-safe라 회원 쪽/비회원 쪽에 독립적으로 적용됨) 회원은 authorId 기준, 비회원은 guestId 기준으로 각각 최대 1개만 가지게 했다 — requests/replies에서 이미 쓴 것과 같은 트릭이라 COALESCE 같은 표현식 유니크 인덱스가 필요 없었다.
- `CHECK (guest_id IS NULL OR status = 'skipped')` — 보류는 회원만 가능하다는 규칙을 DB 레벨에서도 강제.
- 답장을 성공적으로 제출하면 해당 (요청, 조회자) 조합의 `answer_interactions` 행을 지운다(`RepliesService.create()`에서 `AnswerInteractionsService.clearForViewer()` 호출) — 보류해뒀다가 답한 요청은 더 이상 보류함에 남지 않아야 하므로.

## 결정 3: `GET /requests/queue`는 단일 후보 하나만 반환

목록이 아니라 "다음에 답할 것 하나"만 돌려준다 — 프론트가 실제로 필요한 모양(`currentAnswerTarget: OnseolRequest | null`)이 그거라서다. 여러 개를 받아서 클라이언트가 고르는 방식은 캡/신선도/제외 로직을 프론트에도 중복 구현해야 해서 피했다.

## 결정 4: `GET /replies/mine` — 답변 로그용 새 엔드포인트

내가 쓴 답장을 원래 요청과 묶어서 보여주는 엔드포인트가 없어서 추가했다(`replies` 테이블을 `requests`와 조인, 조회자의 답장만 필터링). 로그인 사용자와 게스트 둘 다 쓸 수 있다(둘 다 답장을 쓸 수 있으므로).

## 이번 라운드에서 하지 않은 것

- `/read`용 저장(save) 기능과 그 스키마 — 다음 백엔드 라운드로 미룸.
- `GET /requests` 자체의 뷰어 인지(viewer-aware) 확장 — `/today`는 이미 필요 없었고, `/answer`는 전용 `/requests/queue` 엔드포인트로 해결했으므로 범용 목록 엔드포인트를 굳이 바꾸지 않았다.
- 프론트엔드 연동 — 이 문서는 백엔드만 다룬다.

## 검증

- 단위 테스트(`pnpm --filter api test`, 52개): `answer-interactions.service.spec.ts` 신규, `requests.service.spec.ts`/`replies.service.spec.ts`에 큐·답변로그 테스트 추가.
- 로컬 Postgres + 실제 서버에 `curl`로 직접 검증: 자기 글 제외, 넘기기(회원·비회원)가 다른 조회자에게 전혀 영향 없음, 보류→보류함 표시→답장 시 자동 해제, `/replies/mine` 정확성, 비회원 보류 401, 답장 5개로 캡 도달 시 대안이 있는 한 제외되고 대안이 전부 소진되면 캡 무시하고 다시 나타남(요청 하나에 서로 다른 회원 5명이 답장하게 만들어 직접 확인), 신선도 60시간 초과 요청은 `GET /requests`에는 계속 보이지만 큐에는(대안이 모두 소진돼도) 절대 나타나지 않음(`created_at`을 61시간 전으로 직접 옮겨서 확인).
