# 온설 DB 호스팅 · MVP 신고/관리자 흐름 결정 - 2026-08-21

이 문서는 `docs/decisions/2026-08-14-onseol-product-decisions.md`가 "확정 전에 물어볼 결정"으로 남겨둔 두 항목을 확정한다.

- 첫 실제 데이터베이스를 어디에 둘지
- 신고된 요청/답변을 처리할 최소 관리자/운영 흐름

로그인/내 정보/내 기록으로 넘어가려면 실제 Nest.js 백엔드가 필요한데, 두 항목 모두 백엔드 설계 전에 확정하기로 되어 있던 항목이라 여기서 먼저 정리한다. 이 문서 자체는 애플리케이션 코드를 만들지 않는다 — 실제 Nest.js 백엔드/로그인 설계는 이 결정을 전제로 별도 계획 세션에서 진행한다.

## 결정 1: DB 호스팅

**개인 서버 PostgreSQL로 시작하고, 아래 트리거 중 하나라도 충족하면 AWS/RDS식 managed Postgres로 이전을 검토한다.**

이전 검토 트리거:

- 정전/하드웨어 장애 등으로 실제 서비스 중단을 겪었을 때
- 응답 지연이 사용자 경험에 체감될 때
- 실사용자 수/트래픽이 가정용 인터넷 회선 대역폭 한계에 가까워질 때

### 근거

순정 PostgreSQL을 쓰기로 이미 결정했으므로(Supabase 등 벤더 특화 DB 아님) 개인 서버에서 managed로 나중에 옮기는 비용이 `pg_dump`/`pg_restore` 또는 논리 복제 수준으로 작다. 초기 트래픽 규모에서는 개인 서버 하드웨어가 RDS 최저 티어(버스터블 CPU라 스파이크에 제약)보다 오히려 나을 수 있어, 사전에 정확히 예측하기보다 실측 후 위 트리거 기준으로 이전 여부를 판단하는 편이 합리적이라고 판단했다. 트리거를 미리 정해둔 이유는 "언제 옮길지 애매해서 계속 미루는" 상황을 피하기 위함이다.

개인 서버와 RDS식 managed Postgres의 주요 차이:

- **가용성/장애 복구**: 개인 서버는 단일 장애점(정전, 회선 끊김, 하드웨어 고장). RDS는 자동 백업(PITR), Multi-AZ 옵션으로 자동 failover 제공.
- **성능**: 초기 트래픽에서는 개인 서버가 RDS 최저 티어보다 나을 수 있음(버스터블 CPU 제약 없음).
- **네트워크/보안**: 개인 서버는 방화벽/TLS/포트포워딩/가정용 회선의 느린 업로드 대역폭을 직접 관리해야 함. RDS는 VPC + 보안 그룹으로 퍼블릭 노출을 줄이기 쉬움.
- **비용**: 이미 있는 하드웨어라면 개인 서버는 사실상 전기세 수준. RDS는 최저 사양도 즉시 월 비용 발생.

## 결정 2: MVP 신고/관리자 흐름

### 자동 숨김

같은 대상(요청 또는 답변)에 대해 **서로 다른 사용자 3명**이 신고하면 자동으로 `hidden` 처리한다.

- 같은 사용자의 중복 신고는 카운트를 늘리지 않는다(기존 요구사항 R15).
- 이를 위해 report는 `(targetType, targetId, reporterId)` 조합에 유니크 제약을 둔 별도 테이블/리포지토리로 다룬다. 현재 localStorage 프로토타입처럼 `reportCount`를 단순 증가시키는 방식은 신고자 중복을 걸러낼 수 없어 실제 백엔드에는 그대로 가져가지 않는다.
- 1건 신고 즉시 숨김이 아니라 3명 기준을 둔 이유: 오탐/악의적 신고 1건으로 정상 콘텐츠가 사라지는 것을 막으면서도, 유해 콘텐츠의 노출 시간은 크게 줄이기 위함이다.

### 관리자 식별

별도 role 테이블 없이, **화이트리스트(환경변수 또는 시드 데이터의 user id 목록) 기반**으로 관리 기능 접근을 제한한다. 1인 운영 규모에 맞는 최소 구현이며, 필요해지면 나중에 role 테이블로 확장 가능한 경계(provider 형태)로 둔다.

### 관리 화면

간단한 웹 UI 하나(`/admin`)를 둔다.

- **초기 구현 범위는 "신고 검토" 하나뿐이다**: 자동 숨겨진 요청/답변 목록과 각 항목의 복구/영구 삭제.
- 화면 구조는 섹션을 늘릴 수 있게 잡아둔다(예: nav 또는 탭으로 "신고 검토" 외에 "통계" 등을 나중에 추가할 수 있는 레이아웃). 다만 **통계 등 다른 섹션은 지금 만들지 않는다** — 지금 범위를 넘는 기능을 미리 만들면 스코프가 커진다.
- **복구**: 오탐 신고로 정상 글이 숨겨질 수 있으므로 필요하다. 최소 버전은 `hidden`을 `false`로 되돌리는 것만 한다.
- **영구 삭제**: 실제 DB row 삭제 대신 소프트 삭제(별도 상태 플래그)를 권장한다 — 감사 추적과 실수 복구 가능성을 남기기 위함. 정확한 필드 설계는 실제 백엔드 스키마 설계 단계에서 다룬다.

### 후속 결정 필요 (이 문서에서 확정하지 않음)

- 관리자가 복구한 항목이 재신고로 다시 자동 숨김되지 않도록 "검토 완료" 플래그가 필요한지.
- 악성/반복 신고자에 대한 대응(신고 권한 제한 등) — MVP 범위 밖으로 미룬다.
- `/admin`에 들어갈 통계 등 후속 섹션의 구체적 내용과 시점.
