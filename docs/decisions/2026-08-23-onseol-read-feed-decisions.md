# 온설 읽기 피드(/read) 백엔드 연동 결정 - 2026-08-23

`/read`를 실제 API로 연동하는 라운드에서 정한 결정을 기록한다. 신고 3명 임계치·비회원 글쓰기 정책(`docs/decisions/2026-08-21-*`)과 보류/저장은 로그인 필수라는 정책(`docs/decisions/2026-08-22-onseol-answer-queue-decisions.md`)은 그대로 유지했다.

## 결정 1: 전원 익명 유지, "글쓰기 방식 선택권"은 이번 라운드 범위 밖

`/read`의 "익명 N" 라벨을 실제 API로 재현하려던 중, 더 근본적인 질문(글쓰기를 익명/식별 가능한 이름 중 선택하게 할지)이 나왔다. 다음 이유로 이번 라운드는 지금처럼 전원 익명을 유지하기로 했다:

- 온설의 제품 컨셉 자체가 "누구나 짧게 털어놓고 짧게 위로받는" 익명 기반이라, 선택적 실명/고정 닉네임 노출은 그 전제와 충돌할 수 있다.
- 지금 스키마엔 로그인 사용자도 표시 이름(닉네임) 필드 자체가 없다 — 선택권을 주려면 프로필/닉네임 개념부터 새로 설계해야 하는 더 큰 결정이다.

"글쓰기 방식 선택권"은 별도의 제품 결정으로 미뤄뒀다 — 이번 라운드에서 구현하지 않았다.

## 결정 2: 익명 라벨 = 스레드 범위 + 랜덤 닉네임, `authorId` 노출 없이

`requests`/`replies` 응답은 이미 `authorId`/`guestId`를 절대 내려주지 않는다(`/answer` 라운드에서 이미 정한 설계). `/answer`는 화면에 요청 하나만 보여줘서 문제가 안 됐지만, `/read`는 요청 하나와 그 답장 여러 개를 한 화면에 같이 보여준다 — 같은 게스트가 한 요청에 답장을 여러 번 남긴 경우, 그걸 구분해서 보여줄 신호가 프론트엔드엔 전혀 없다.

- **`authorSlot` (백엔드, `src/requests/feed-author-slots.ts`)**: 스레드 안에서 처음 등장한 순서대로 신원(회원이면 `authorId`, 게스트면 `guestId`)에 0, 1, 2, ...를 매긴다. 같은 신원이 그 스레드 안에서 다시 나오면 같은 슬롯을 재사용한다. 이 슬롯 값 자체는 실제 신원을 전혀 담지 않고, 다른 스레드로도 이어지지 않는다 — `GET /requests/feed` 응답에 `authorId` 대신 이것만 실린다.
- **랜덤 닉네임 (프론트엔드, `apps/web/app/read/labels.ts`)**: `authorSlot` 숫자를 화면에 그대로 보여주는 대신("익명 1/2/3" 순번 대신), 고정된 한글 닉네임 풀에서 스레드의 `request.id`를 해시한 오프셋으로 골라 보여준다 — 같은 스레드는 새로고침해도 같은 닉네임을 유지하지만, 스레드마다 다른 닉네임에서 시작한다.

기존 프로토타입은 `authorId` 기준으로 피드 전체에 걸쳐 같은 사람에게 같은 번호를 유지했지만, 실제 API로는 재현이 불가능하다(애초에 `authorId`가 없음) — 사용자에게 이 tradeoff를 설명하고 스레드 범위로 좁히는 데 동의를 받았다.

## 결정 3: `GET /requests/feed` — 새 엔드포인트, 답장 있는 요청만 반환

`GET /requests`는 `replyCount`만 주고 답장 내용은 안 준다. `/read`는 답장 내용까지 필요해서 전용 엔드포인트를 추가했다: 답장이 하나라도 있는(그리고 숨겨지지 않은) 요청만, 요청 최신순으로, 각 요청의 답장은 오래된 순으로 중첩해서 반환한다. 페이지네이션은 기존 `GET /requests`도 없는 상태라 이번에도 추가하지 않았다.

구현은 두 번의 단순 쿼리(요청 목록 → 그 요청들의 답장 일괄 조회 → 메모리에서 그룹핑)로 했다 — `findQueueCandidate`와 같은 이유(명확성 우선, 복잡한 조인 서브쿼리보다 검증하기 쉬움).

## 결정 4: 저장(save) — `saved_replies` 별도 테이블, 회원 전용

이전 라운드에서 이미 "로그인 필수"로 정해뒀던 것을 그대로 구현했다. `answer_interactions`처럼 재사용하지 않고 별도 테이블/모듈(`src/saved-replies/`)로 만들었다 — 보류는 "조회자당 요청 1개, 상태 하나"인 배타적 관계지만 저장은 "회원 하나가 답장 여러 개를 저장"하는 순수 다대다 북마크라 성격이 다르다고 판단했다. `unique(replyId, authorId)`로 중복 저장을 막고, save/unsave 둘 다 멱등(idempotent)하게 만들었다(`onConflictDoNothing`/무조건 삭제) — 프론트에서 낙관적으로 두 번 눌러도 에러가 나지 않게.

## 이번 라운드에서 하지 않은 것

- 글쓰기 방식 선택권(익명/식별 가능한 이름) — 결정 1 참고, 별도 라운드.
- 저장한 답변 전체를 보여주는 화면(`/me`류) — `GET /replies/saved`는 지금 답장 id 배열만 반환한다. 실제 내용까지 보여주는 화면이 생기면 그때 응답 모양을 넓힌다.

## 검증

- 단위 테스트(`pnpm --filter api test`, 55개): `feed-author-slots.spec.ts` 신규(슬롯 배정 규칙 3가지).
- 로컬 Postgres + 실제 서버에 `curl`로 직접 검증: `GET /requests/feed` 응답에 `authorId`/`guestId` 없음, `authorSlot`이 요청 작성자=0/답장 작성자=1로 정확히 나뉨, 저장 없이 세션 없이 호출 시 401(`POST/DELETE /replies/:id/save`, `GET /replies/saved`), save→saved 목록에 반영→unsave→목록에서 사라짐 각 단계 멱등성(두 번 호출해도 204), 존재하지 않는/숨겨진 답장 저장 시도 시 404.
