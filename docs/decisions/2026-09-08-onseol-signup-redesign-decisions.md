# 온설 회원가입 재설계 결정 기록 (이메일 인증 선행 방식)

> 이 문서는 실시간 대화 기록이 아니라, 이미 머지된 PR #143/#145의 커밋 메시지·PR 본문·실제 diff를 근거로 사후 재구성한 기록이다(작성 시점 기준 다른 세션에서 진행된 작업). 커밋/PR에 명시된 내용만 담았고, 실제 논의 과정에서 오간 대화나 대안 검토는 원본 자료에 남아있지 않아 포함하지 않았다.

## 배경

`docs/decisions/2026-08-28-onseol-email-verification-decisions.md`에서 만든 최초 이메일 인증 모델은 "회원가입 시 계정을 즉시 만들되 `emailVerifiedAt`이 null인 미인증 상태로 두고, 미인증 회원은 게스트와 같은 답장 상한을 적용"하는 방식이었다. PR #143(2026-09-07 머지)이 이 모델의 프론트엔드(`/verify-email` 소비 페이지, 가입 직후 안내 화면, `/me` 미인증 배지 + 재발송 버튼)를 붙여 실제로 쓸 수 있게 만들었다.

바로 다음 PR #145(2026-09-07 머지, 커밋 `0877296`)에서 이 모델 자체가 근본적으로 재설계됐다.

## 결정: 계정은 이메일 소유를 증명한 뒤에만 생성된다

기존 모델(계정 먼저 생성 → 나중에 인증)에서 "이메일 인증 선행" 모델(인증 먼저 → 그 순간 계정 생성)로 전환:

- `POST /auth/signup`은 이제 이메일만 받고 계정을 만들지 않는다 — `pending_signups` 테이블에 토큰만 발급하고 인증 메일을 보낸다.
- 그 링크를 눌러 비밀번호를 설정하는 `POST /auth/complete-signup` 호출 시점에 비로소 이미 인증된 `users` 행이 생성되고, 동시에 세션이 발급돼 자동 로그인된다.
- 로그인은 미인증 상태(레거시 데이터)에 대해 항상 거부된다 — `EmailNotVerifiedException`(403, `AUTH_EMAIL_NOT_VERIFIED`). 커밋 메시지는 이를 "레거시 데이터 대비용 방어 코드"로 명시한다 — 새 플로우로 만들어진 계정은 애초에 미인증 상태로 존재할 수 없기 때문이다.

**근거(커밋 메시지 원문)**: "이 덕분에 남의 이메일로 미리 가입해서 선점/방해하는 것 자체가 불가능해진다('제출'이 곧 '이메일함에 도달'일 뿐 아무것도 만들지 않음)."— 기존 모델은 계정을 먼저 만들었기 때문에, 타인의 이메일로 가입을 시도하는 것만으로 그 이메일 소유자의 향후 가입을 막을 수 있는 여지가 있었다는 뜻으로 읽힌다.

## 부수 효과: "미인증 회원" 개념 자체가 사라짐

이 재설계로 다음 두 가지가 더 이상 존재할 수 없는 상태가 되어 제거됨:

- 답장 상한 우회 방지 로직(`ReplyUnverifiedLimitExceededException`) — 미인증 회원이라는 상태 자체가 없어졌으므로.
- OAuth 로그인 시 미인증 계정 격리(quarantine) 로직 — 마찬가지 이유.

남은 유일한 레거시 케이스: 예전 모델로 만들어진 미인증 계정을, 나중에 OAuth 로그인이 시도될 때 그 자리에서 인수(identity 연결 + 인증 처리 + 비밀번호 초기화)하는 경로만 남김.

## 함께 처리된 OAuth 이메일 검증 신호 버그 수정

같은 PR에서 함께 수정(커밋 메시지 기준):

- Kakao(`is_email_valid`)/Google(`email_verified`) 두 provider가 실제로 제공하는 이메일 검증 신호를 이전엔 확인하지 않고 있었는데, 이제 실제로 확인하도록 수정.
- 세션 상태에서 소셜 계정을 연동(`linkOAuth`)할 때, 연동하려는 계정의 이메일이 실제 로그인 계정 이메일과 다른 경우에도 잘못 인증 처리되던 버그 수정.

## PR #143에서 만들었던 프론트엔드 중 이번에 제거된 것

PR #143이 추가했던 `apps/web/app/me/components/EmailVerificationBadge.tsx`(미인증 배지 + 재발송 버튼, 59줄)는 이 재설계로 "세션이 있으면 항상 인증된 상태"가 성립하게 되면서 존재 이유가 없어져 이번 PR에서 그대로 삭제됨(diff 기준 59줄 삭제, 신규 `LinkedProvidersSection.tsx` 55줄로 대체). `/verify-email`의 토큰 소비 폼(`VerifyEmailForm.tsx`)은 유지하되, 이제 여기서 비밀번호를 함께 입력받아 `complete-signup`을 호출하는 방식으로 바뀜(기존엔 토큰 검증만 하는 별도 엔드포인트였음).

## 현재 상태로 남은 필드/한계

- `GET /auth/me` 응답의 `emailVerified` 필드(boolean, `emailVerifiedAt !== null`로 계산)는 API에 그대로 남아있지만, 새 모델에서는 세션을 가진 계정이 항상 `true`이므로 사실상 죽은 필드다 — 레거시 대비용으로 유지할지, 정리할지는 아직 결정된 바 없음.
- `POST /auth/signup`의 "재발송"은 별도 엔드포인트 없이 같은 엔드포인트를 다시 호출하는 것과 동일하다. `AuthService.requestSignup`은 이미 존재하는 `users` 행만 확인하고, 아직 소비되지 않은 기존 `pending_signups` 토큰이 있는지는 확인하지 않는다 — 같은 이메일로 여러 번 요청하면 유효한 토큰이 동시에 여러 개 존재할 수 있다(기능적으로 깨지진 않음 — 그중 어느 토큰으로도 가입 완료 가능 — 하지만 의도된 설계라기보단 하드닝되지 않은 지점).
