# 위로/칭찬 교환 서비스 피벗 설계

## 개요

이 제품은 기존의 "칭찬 커뮤니티"에서 더 가볍고 접근하기 쉬운 "익명 위로/칭찬 교환 서비스"로 방향을 바꾼다.

사용자는 오늘 위로받고 싶은 일을 짧게 남기거나, 다른 사람이 남긴 위로 요청에 담백한 답변을 남긴다. 커뮤니티 활동량, 랭킹, AI 댓글 자동화보다 중요한 약속은 하나다. 사용자가 막막한 순간에 들어와서 복잡한 설명 없이 "내 이야기를 남기거나, 누군가에게 한마디 건네는" 행동을 바로 할 수 있어야 한다.

한강물 온도 사이트처럼 단순하고 쉽게 접근할 수 있는 분위기는 참고하되, 동일한 콘셉트나 화면 구조를 따르지는 않는다. 이 서비스의 중심 은유는 수치 자체가 아니라 오늘의 온기, 최근 사람들이 주고받은 담백한 말, 그리고 작게 이어지는 익명 교환이다.

## 제품 원칙

- MVP는 웹부터 만든다. 모바일 앱과 푸시 알림은 이후 확장 대상으로 둔다.
- 첫 화면은 커뮤니티 피드가 아니라 오늘의 행동 선택을 중심에 둔다.
- 사용자가 오늘 위로 요청을 쓰지 않았다면 그 사실을 알려주고, `위로 요청하기`와 `다른 사람에게 답변하기` 중 하나를 고르게 한다.
- 글쓰기 입력은 단순해야 한다. "마음 온도" 같은 의미가 불명확한 입력은 MVP에서 제외한다.
- 위로 요청과 답변은 현실적이고 담백한 톤을 기본으로 한다. 과장된 감성, 상담사 같은 조언, 문제 해결 강요, 오글거리는 문구는 피한다.
- 익명은 공개 표시상의 익명이다. 운영, 신고, 제재, 중복 답변 제한은 계정 또는 임시 로컬 작성자 식별자와 연결된다.
- 안전, 신고, 콘텐츠 품질 관리는 부가기능이 아니라 MVP의 필수 조건이다.
- "화로" 또는 온기 표현은 핵심 기능이 아니라 오늘의 분위기를 보여주는 보조 시각 요소로 둔다.

## MVP 범위

MVP에 포함한다:

- 소개 페이지.
- 웹에서 바로 이용하는 메인 화면.
- 오늘 위로 요청 작성 여부 안내.
- 위로 요청 작성.
- 다른 사람의 위로 요청에 답변 작성.
- 최근 위로 요청과 답변 예시 섹션.
- 로그인 전 로컬 임시 저장과 로그인 후 이어받기.
- 신고, 기본 필터링, 콘텐츠 품질 게이트.
- 내 위로 요청 목록.
- 내가 답변한 목록.
- 답변을 처음 받았을 때의 인앱 알림 기반 구조.
- 오늘의 분위기/온기 표시.

MVP에서 제외한다:

- 네이티브 모바일 앱.
- 푸시 알림.
- 이미지 또는 배경 이미지 업로드.
- 랭킹 중심 구조.
- 좋은 말 쓰기 시즌 기능.
- 고도화된 프로필 꾸미기.
- DM, 친구, 팔로우.
- AI가 사람처럼 자동 댓글을 쓰는 기능.
- 공개 활동량 경쟁.
- AI 답변 fine-tuning.
- 기존 `PraisePost`/`PraiseComment` 도메인 재사용.

후순위로 둔다:

- 수능, 연말, 새해 같은 시즌별 좋은 말 주제.
- 모바일 앱 푸시 알림.
- 사용자가 선택할 수 있는 기본 배경 또는 캐릭터 테마.
- 온기 변화 애니메이션.

## 핵심 화면

### 소개 페이지

소개 페이지는 서비스의 설명을 길게 늘어놓지 않는다. 첫 방문자는 두 가지 선택지만 본다.

- `앱 설치하러 가기`
- `웹에서 이용하기`

MVP에서는 앱 설치가 준비되지 않았으므로 앱 버튼은 비활성 또는 준비 중 상태로 둘 수 있다. 핵심 진입은 `웹에서 이용하기`다.

### 메인 화면

메인 화면은 세 부분으로 구성한다.

1. 오늘 상태 안내.
2. 최근 위로/답변 섹션.
3. 행동 선택 영역.

오늘 상태 안내는 사용자가 오늘 아직 위로 요청을 쓰지 않았다면 다음 의미를 짧게 알려준다.

> 오늘은 아직 위로 요청을 남기지 않았어요.

그 아래에서 사용자는 `위로 요청하기` 또는 `다른 사람에게 답변하기`를 선택한다. 이 선택은 탭 또는 세그먼트 컨트롤처럼 동작하며, 사용자의 현재 목적을 바꾼다.

### 최근 위로/답변 섹션

최근 위로/답변 섹션은 "내가 받은 위로"가 아니다. 처음 온 사용자가 어떻게 쓰면 되는지 감을 잡을 수 있게 실제 최신 데이터를 보여주는 예시와 분위기 영역이다.

노출 기준:

- 실제 데이터만 사용한다.
- 신고되었거나 필터에 걸린 콘텐츠는 제외한다.
- 너무 긴 요청과 답변은 일부만 보여준다.
- 답변이 달린 요청을 우선 노출한다.
- 요청 하나당 미리보기 답변은 1-2개 정도만 보여주고, 자세한 내용은 상세 화면에서 확인한다.

PC에서는 메인 상단에 최근 위로/답변 섹션을 먼저 배치한다. 모바일에서는 상단 요약과 접기/펼치기 패널을 기본으로 한다. 드래그해 펼치는 패널은 첫 구현의 사용성이 부족할 때 개선안으로 검토한다.

## 위로 요청 작성

위로 요청 작성은 단일 textarea를 기본으로 한다.

권장 라벨:

> 오늘 어떤 말을 듣고 싶나요?

권장 placeholder:

> 오늘 있었던 일이나 듣고 싶은 말을 짧게 적어주세요.

작성 정책:

- 하루에 작성 가능한 요청 수는 MVP에서 1개로 시작한다.
- 로그인 전 작성 내용은 로컬에 저장한다.
- 로그인 또는 회원가입이 끝나면 로컬 작성 내용을 계정에 이어붙인다.
- 너무 짧거나 의미 없는 내용, 위험 표현, 공격적 표현은 저장 전 필터링한다.
- 사용자가 원하면 공개 표시를 익명으로 둔다.

하루 1개 제한은 서비스의 목적을 명확히 하고, 스팸과 과도한 피드 점유를 줄인다. 하루 제한 완화는 실제 사용 데이터가 쌓인 뒤 별도 변경으로 다룬다.

## 답변하기

답변하기 화면은 아직 답변을 더 받을 수 있는 위로 요청을 하나씩 보여준다. 정렬은 다음을 우선한다.

- 오늘 올라온 요청.
- 답변이 아직 적은 요청.
- 신고/필터를 통과한 요청.
- 사용자가 아직 답변하지 않은 요청.

답변 정책:

- 한 요청에는 여러 명이 답변할 수 있게 한다.
- 한 사람은 한 요청에 답변 1개만 남길 수 있다.
- 답변 1개는 최대 1000자까지 허용한다.
- 한 요청에 표시되는 답변은 최대 4-5개를 기본으로 한다.
- 답변은 작성자별 말풍선 하나로 표시한다.
- 여러 줄 입력은 허용하지만 여러 말풍선으로 쪼개지는 채팅 전송은 MVP에서 제외한다.

한 사람의 답변을 말풍선 하나로 제한하는 이유는 최근 위로/답변 섹션과 상세 화면에서 여러 응답자가 섞일 때 시각적으로 복잡해지는 것을 막기 위해서다.

답변 톤 가이드:

- "그럴 수 있어요"처럼 현실을 인정하는 말.
- "오늘은 여기까지 온 것만으로도 충분해요"처럼 과하지 않은 지지.
- 해결책을 강요하지 않는 문장.
- 상대의 상황을 단정하지 않는 문장.
- AI가 쓴 것처럼 보이는 문장 패턴과 과한 문어체는 피한다.

## AI 역할

MVP에서 AI가 사람처럼 자동 댓글을 게시하는 기능은 제외한다. AI는 답변자인 척하지 않고 작성 보조와 안전 필터 역할에 집중한다.

AI를 사용할 수 있는 위치:

- 사용자가 답변을 쓰기 어려워할 때 참고할 수 있는 보조 초안.
- 운영자가 검수할 수 있는 예시 답변 후보.
- 비꼼, 무의미 글, 위험 표현, 홍보성 글을 판정하는 콘텐츠 품질 게이트.
- 향후 시즌별 좋은 말 생성의 검수 전 후보.

공개 답변은 사람의 선택과 제출을 거친다. AI 초안이 사용자에게 제안되더라도 사용자가 그대로 게시할 수 있게 두지 않고, 최소한 수정 또는 확인 행동을 거치게 한다.

## AI 답변 품질 루프

이때 목표는 모델을 바로 fine-tuning하는 것이 아니다. 초기에는 좋은 답변과 나쁜 답변 기준을 명확히 만들고, 생성 결과를 저장 전 평가하는 루프를 구축한다.

AI 답변 생성은 다음 단계를 따른다.

1. 위로 요청 본문과 노출 가능한 맥락만 입력으로 사용한다.
2. 담백한 한국어 위로 톤의 좋은 예시와 나쁜 예시를 프롬프트에 함께 제공한다.
3. AI가 2-3개의 후보 답변을 생성한다.
4. 별도의 품질 평가기가 후보를 점수화한다.
5. 기준 점수를 넘은 후보만 사용자 보조 초안 또는 운영 검수 대상으로 사용한다.
6. 기준을 넘지 못하면 재생성하거나 AI 제안을 표시하지 않는다.

품질 평가기는 다음 항목을 본다.

- 원글 내용과 실제로 연결되어 있는가.
- 너무 일반론적이거나 어디에나 붙일 수 있는 문장인가.
- 과하게 상담사처럼 말하거나 해결책을 강요하는가.
- 상대의 상황, 감정, 원인을 단정하는가.
- "힘내세요", "당신은 소중합니다"처럼 반복적이고 AI 티가 나는 문장인가.
- 위로가 아니라 평가, 훈계, 조언, 자기 이야기로 중심이 옮겨졌는가.
- 한국어 문장이 자연스럽고 말투가 과장되지 않았는가.

운영자는 AI 후보에 대해 `좋음`, `별로`, `차단` 같은 간단한 판정을 남길 수 있다. 이 판정은 즉시 모델 학습에 쓰기보다 다음에 사용한다.

- 좋은 예시와 나쁜 예시 프롬프트 갱신.
- 품질 평가 기준 조정.
- 회귀 테스트용 fixture 구성.
- 향후 fine-tuning 또는 별도 classifier 학습 여부 판단.

fine-tuning은 좋은/나쁜 답변 데이터가 충분히 쌓인 뒤 검토한다. MVP에서는 few-shot 예시, LLM 기반 평가, 운영자 피드백 데이터셋을 우선한다.

## 익명과 로컬 이어받기

로그인 전 사용자는 위로 요청 또는 답변 초안을 작성할 수 있게 한다. 이 데이터는 서버 계정이 아니라 브라우저 로컬 저장소에 임시 보관한다.

로그인 후 이어받기 흐름:

1. 로컬에 저장된 위로 요청 또는 답변 초안이 있는지 확인한다.
2. 사용자에게 이어받을 내용을 보여준다.
3. 사용자가 확인하면 서버 계정에 연결해 저장한다.
4. 저장이 끝나면 로컬 임시 데이터를 제거한다.

익명 사용 중에도 남용을 완전히 방치하지 않는다. 로그인 전에는 브라우저 기반 임시 작성자 식별자를 사용해 중복 제출, 반복 신고, 과도한 작성 시도를 제한한다. 중요한 쓰기 행동의 최종 저장 또는 알림 수신은 계정 연결을 우선한다.

## 알림

MVP의 알림은 웹 인앱 알림을 기준으로 한다.

- 내가 쓴 위로 요청에 첫 답변이 달렸을 때 알림을 만든다.
- 이후 추가 답변 알림은 과도하게 쌓이지 않도록 묶거나 낮은 우선순위로 둘 수 있다.
- 모바일 앱 푸시 알림은 앱 구현 단계에서 추가한다.

## 내 정보

내 정보 화면은 다음을 포함한다.

- 내가 쓴 위로 요청 목록.
- 내가 답변한 요청 목록.
- 계정 정보와 닉네임 설정.
- 공개 표시 기본값.
- 알림 설정.

페이지네이션과 날짜 정렬은 기존 프로젝트의 내 활동 흐름을 재사용한다.

## 신고와 필터

신고와 필터는 다음 대상으로 동작한다.

- 위로 요청.
- 답변.
- 사용자 계정.

기본 처리:

- 위험하거나 공격적인 내용은 작성 시점에 차단 또는 보류한다.
- 신고된 콘텐츠는 운영 검토 전까지 노출 범위를 줄일 수 있다.
- 반복 신고와 반복 위반은 신뢰 점수 또는 쓰기 제한에 반영한다.
- 신고자에게 필터 우회 힌트를 주지 않는다.

자해, 자살, 긴급 위험 표현은 일반 위로 답변 흐름으로만 처리하지 않는다. 별도의 안전 문구와 도움 요청 안내를 보여주고, 해당 콘텐츠는 운영 검토 대상으로 보낸다.

## 콘텐츠 품질 게이트

필터링은 단어 금칙어 목록으로만 처리하지 않는다. 위로 서비스에서는 욕설보다 더 미묘한 상처가 문제가 될 수 있다. 예를 들어 비꼼, 칭찬처럼 보이는 공격, 별일 아닌 취급, 의미 없는 도배, 원글과 무관한 답변은 모두 별도 품질 판정 대상이다.

작성된 위로 요청과 답변은 저장 또는 노출 전에 다층 품질 게이트를 지난다.

### 1차 빠른 규칙 검사

서버에서 비용이 낮은 규칙 검사를 먼저 수행한다.

- 공백 제거 후 최소 길이 미달.
- 같은 글자, 자모, 이모티콘, 문장 반복.
- URL, 홍보, 구독 유도, 외부 채널 유도.
- 지나치게 높은 특수문자 비율.
- 같은 사용자의 짧은 시간 내 유사 내용 반복.
- 이전에 차단된 내용과 거의 같은 문장.

이 단계는 명확한 스팸과 의미 없는 글을 빠르게 걸러낸다. 애매한 글은 바로 차단하지 않고 다음 단계로 넘긴다.

### 2차 의미 기반 분류

규칙으로 판단하기 어려운 글은 의미 기반 분류를 거친다. 분류기는 원문과 함께 다음 라벨을 반환한다.

- `supportive`: 정상 위로 또는 칭찬.
- `low_effort`: 의미 없음, 성의 없음, 내용 부족.
- `sarcastic`: 비꼼, 조롱, 빈정거림.
- `backhanded`: 칭찬인 척하는 공격.
- `dismissive`: 별일 아닌 취급, 감정 축소.
- `advice_pushing`: 조언 강요, 해결책 강요.
- `self_centered`: 상대보다 자기 이야기 중심.
- `unsafe`: 자해, 폭력, 혐오, 성적 위험, 긴급 위험.
- `spam`: 홍보, 반복, 무관한 글.

분류기는 라벨, 점수, 짧은 이유를 반환한다. 사용자에게는 내부 라벨과 우회 가능한 상세 이유를 노출하지 않는다.

### 3차 맥락 기반 판정

답변은 답변 본문만으로 판단하지 않는다. 같은 문장도 원글 맥락에 따라 위로가 될 수도 있고 비꼼이 될 수도 있다.

예를 들어 "대단하시네요"는 단독으로는 긍정 문장처럼 보이지만, 원글 내용과 함께 봤을 때 조롱이 될 수 있다. 따라서 답변 품질 판정은 위로 요청 본문, 답변 본문, 작성자의 이전 반복 패턴을 함께 본다.

### 4차 사용자 행동 신호

콘텐츠 하나의 문장만으로 판정하지 않고 사용자 행동도 반영한다.

- 같은 사용자가 여러 요청에 거의 같은 답변을 남기는가.
- 작성 직후 신고가 반복되는가.
- 이전에 `AUTHOR_ONLY`, `HELD`, `HIDDEN` 처리된 비율이 높은가.
- 낮은 신뢰 점수 사용자가 경계 점수 콘텐츠를 반복 작성하는가.

행동 신호는 즉시 차단의 유일한 근거로 쓰지 않고, 노출 상태와 운영 검토 우선순위를 정하는 보조 점수로 사용한다.

### 노출 결정

품질 게이트 결과는 다음 상태 중 하나로 이어진다.

- `VISIBLE`: 즉시 노출.
- `AUTHOR_ONLY`: 작성자에게는 보이지만 다른 사용자에게는 보이지 않음.
- `HELD`: 운영 검토 전까지 보류.
- `HIDDEN`: 명확한 위험 또는 반복 위반으로 숨김.

욕설, 명확한 혐오, 자해 조장, 폭력 위협, 홍보 도배는 `HIDDEN` 또는 `HELD`로 간다. 비꼼, 뒷맛 나쁜 칭찬, 별일 아닌 취급, 의미 없는 답변처럼 애매하지만 서비스 분위기를 해치는 글은 우선 `AUTHOR_ONLY` 또는 `HELD`로 보낸다.

### 테스트와 운영 피드백

품질 게이트는 회귀 테스트 가능한 예시 세트를 가진다. 예시 세트에는 정상 위로, 애매한 위로, 비꼼, 공격적 조언, 무의미 글, 홍보, 위기 표현을 포함한다.

운영자가 보류 콘텐츠를 `공개`, `작성자 전용`, `숨김`으로 처리한 결과는 품질 게이트 개선 데이터가 된다. 목표는 모든 애매한 문장을 완벽하게 자동 판정하는 것이 아니라, 사용자가 상처받을 가능성이 큰 글의 노출을 줄이고 운영자가 학습 가능한 결정을 쌓는 것이다.

## 오늘의 온기와 화로

화로는 활동 보상 시스템이 아니라 분위기 표시다.

MVP에서는 다음 정도만 표현한다.

- 오늘 오간 위로 요청 수.
- 오늘 달린 답변 수.
- 답변받지 못한 요청이 적을수록 따뜻해지는 상태.

시각적으로는 작은 화로, 온기 게이지, 색 변화 정도로 시작한다. 활동이 뜸하면 재가 되는 장기 캐릭터 시스템은 MVP 이후로 미룬다.

## 기존 기능 재사용과 축소

재사용한다:

- Auth.js 기반 로그인과 네이버 OAuth.
- 닉네임 온보딩.
- Prisma 데이터 계층.
- 신고, 운영자 검토, 제재, 신뢰 점수 구조.
- 알림 구조.
- AI provider 연동과 AI 사용량 기록 구조.
- 페이지네이션과 날짜 정렬 패턴.
- `npm run verify` 기반 검증 규약.

대체하거나 제거한다:

- `PraisePost`, `PraiseComment` 중심 도메인 모델.
- `Reaction`, `Reply` 중심의 감사 반응/작성자 답글 구조.
- `AiPraiseJob` 기반 자동 칭찬 댓글 worker.
- `RankingSnapshot` 기반 랭킹 구조.
- 랭킹 페이지.
- 공개 커뮤니티 피드 중심 UX.
- AI 자동 칭찬 댓글.
- 감사 반응과 작성자 답글 중심의 칭찬방 UX.
- 운영자 화면의 AI 제어가 핵심인 배치.

## 데이터 모델 방향

운영 데이터가 아직 없으므로 기존 칭찬 커뮤니티 데이터와 모델을 보존하기 위한 마이그레이션은 MVP 필수 조건이 아니다. 피벗 구현은 `ComfortRequest`와 `ComfortReply` 신규 모델을 기준으로 한다.

기존 `PraisePost`와 `PraiseComment`를 의미만 바꿔 재사용하지 않는다. 이유는 다음과 같다.

- 기존 모델은 제목, 프롬프트 답변, 칭찬 댓글, 감사 반응, AI 칭찬 작업, 랭킹과 강하게 연결되어 있다.
- 새 서비스는 위로 요청의 문맥을 파악하고, 칭찬과 위로 중 어떤 톤이 필요한지 판단하며, 한 사람당 한 답변만 허용해야 한다.
- 기존 이름과 relation을 유지하면 코드와 문서에 "칭찬글", "칭찬방", "AI 칭찬", "랭킹"의 의미가 계속 남아 다음 작업자의 판단을 흐릴 가능성이 높다.
- 현재 데이터는 운영 데이터가 아니므로 도메인 모델을 새로 세우는 비용보다 장기 혼동을 줄이는 가치가 크다.

### ComfortRequest

위로 또는 칭찬을 받고 싶은 일을 나타낸다.

주요 필드:

- `id`
- `authorUserId`
- `displayMode`: `NICKNAME` 또는 `ANONYMOUS`
- `body`
- `status`: `VISIBLE`, `HELD`, `HIDDEN`, `AUTHOR_ONLY`
- `qualityScore`
- `qualityLabel`
- `firstRepliedAt`
- `createdAt`
- `updatedAt`

정책:

- 사용자당 하루 1개 작성을 기본으로 한다.
- 오늘 작성 여부 조회를 빠르게 할 수 있도록 `authorUserId`, `createdAt` 인덱스를 둔다.
- 최근 위로/답변 섹션을 위해 `status`, `createdAt`, `firstRepliedAt` 기준 조회를 고려한다.

### ComfortReply

위로 요청에 대한 사람의 답변을 나타낸다.

주요 필드:

- `id`
- `requestId`
- `authorUserId`
- `displayMode`: `NICKNAME` 또는 `ANONYMOUS`
- `body`
- `status`: `VISIBLE`, `HELD`, `HIDDEN`, `AUTHOR_ONLY`
- `qualityScore`
- `qualityLabel`
- `createdAt`
- `updatedAt`

정책:

- `body`는 최대 1000자다.
- 한 사용자는 한 요청에 답변 1개만 남길 수 있다.
- 이를 위해 `(requestId, authorUserId)` unique 제약을 둔다.
- 최근 위로/답변 섹션에서는 요청 하나당 1-2개만 미리보기로 가져오고, 상세에서는 최대 4-5개 노출을 기본으로 한다.

### ContentQualityReview

위로 요청, 답변, AI 보조 답변 후보의 품질 판정 결과를 기록한다.

주요 필드:

- `id`
- `targetType`: `COMFORT_REQUEST`, `COMFORT_REPLY`, `AI_REPLY_SUGGESTION`
- `targetId`
- `label`: `supportive`, `low_effort`, `sarcastic`, `backhanded`, `dismissive`, `advice_pushing`, `self_centered`, `unsafe`, `spam`
- `score`
- `reason`
- `modelProvider`
- `modelName`
- `createdAt`

이 테이블은 운영자 판정과 품질 게이트 개선을 위한 데이터셋 역할을 한다.

### AiReplySuggestion

AI가 공개 댓글을 직접 작성하지 않고, 보조 초안 또는 운영 검수 후보를 저장하는 모델이다.

주요 필드:

- `id`
- `requestId`
- `suggestedForUserId`
- `body`
- `qualityScore`
- `qualityLabel`
- `status`: `CANDIDATE`, `SHOWN`, `DISMISSED`, `ADOPTED`, `REJECTED`
- `provider`
- `model`
- `createdAt`
- `updatedAt`

AI 사용량 기록은 기존 `AiUsageEvent` 구조를 일반화해서 사용할 수 있다. 기존 `AiPraiseJob`은 자동 칭찬 댓글 전용이므로 피벗 MVP에서는 제거하거나 비활성화한다.

### Notification

기존 알림은 `postId`가 필수라 위로 요청/답변 모델에 그대로 맞지 않는다. 피벗 구현에서는 다음 중 하나를 선택한다.

1. 기존 `Notification`을 `comfortRequestId`, `comfortReplyId`를 받을 수 있게 일반화한다.
2. 기존 알림 테이블을 교체하고 `targetType`, `targetId` 기반의 범용 알림으로 단순화한다.

운영 데이터가 없으므로 2안을 우선 검토한다. MVP 알림의 첫 목표는 내가 쓴 위로 요청에 첫 답변이 달렸을 때 알림을 만드는 것이다.

### Report와 ModerationEvent

신고와 운영 이벤트는 유지하되 target enum을 새 도메인에 맞춘다.

- `COMFORT_REQUEST`
- `COMFORT_REPLY`
- `AI_REPLY_SUGGESTION`
- `USER`

기존 `POST`, `COMMENT`, `REPLY`는 피벗 마이그레이션에서 제거하거나 더 이상 사용하지 않는다.

## 성공 기준

첫 MVP 피벗이 성공했다고 볼 수 있는 기준:

- 신규 사용자가 첫 화면에서 10초 안에 `위로 요청하기` 또는 `답변하기` 중 하나를 이해하고 선택한다.
- 사용자는 하루 첫 위로 요청 여부를 명확히 알 수 있다.
- 위로 요청 작성은 단일 입력으로 끝난다.
- 답변자는 요청 하나에 답변 하나만 남길 수 있다.
- 최근 위로/답변 섹션은 실제 데이터 기반이며 신고/필터 대상은 보이지 않는다.
- 로그인 전 작성한 내용은 로그인 후 이어받을 수 있다.
- 첫 답변 알림이 생성된다.
- 서비스 전반의 문구가 담백하고 현실적인 톤을 유지한다.
- 비꼼, 성의 없는 글, 무관한 글, 칭찬처럼 보이는 공격은 단어 금칙어가 없어도 품질 게이트에서 걸러진다.
- AI 보조 답변은 사용자에게 제안하기 전 품질 평가를 통과해야 하며, AI 티가 나는 일반론 문장은 사용자에게 제안하지 않는다.

## 열어둘 결정

- 하루에 답변할 수 있는 요청 수 제한은 실제 스팸과 참여 데이터를 보고 결정한다.
- 한 요청의 전체 답변 저장 개수는 MVP에서는 제한하지 않고, 노출 개수만 4-5개로 제한한다.
- 최근 위로/답변 섹션의 모바일 표현은 첫 구현에서는 접기/펼치기로 시작하고, 사용성이 부족하면 드래그 패널로 개선한다.
- 좋은 말 쓰기와 시즌 주제는 MVP 이후 별도 설계로 분리한다.
- 화로의 장기 성장/냉각 시스템은 MVP 이후 별도 설계로 분리한다.
- AI 보조 답변을 사용자에게 직접 보여줄지, 운영 검수용 후보로만 둘지는 구현 계획 단계에서 결정한다.
