# 온설 읽기 피드 스펙

## 목적

`docs/superpowers/specs/2026-08-17-onseol-ux-ia-redesign.md`는 `/read`를 "다른 사람의 요청과 답변을 읽는 화면"으로 정의했지만, 콘텐츠 단위의 상세보기 방식과 `마음에 남기기`의 시각 상징은 "후속 결정 필요"로 남겨두었다. 이 문서는 그 두 가지를 확정하고, `/read` 구현에 필요한 화면 규칙을 정리한다.

## 배경

- 2026-08-17 문서는 `/read` 콘텐츠 단위를 "요청 본문 + 답변 일부 또는 대표 답변 + 작성 시각 + 마음에 남기기"로 정의하고, "긴 내용은 일부만 보여주고 상세/펼침에서 전체를 읽게 한다"고 적었다.
- 이번 논의에서 `/answer` 구현 때 만든 채팅 버블 시각 문법을 재사용하되, 대표 답변 1개만 보여주는 대신 **요청에 달린 모든 답변을 처음부터 전부 보여주는 방식**으로 방향을 바꿨다. 그 결과 "긴 텍스트를 자르고 펼치는" 원래 방식은 채택하지 않는다.
- `/answer`의 답하기 큐는 본인 글을 제외하지만, `/read`는 "다른 사람 글만 보는 소비형 피드"가 아니라 전체 공개 피드로 다루기로 했다 — 본인이 쓴 요청도 다른 사람 것과 동일하게 노출된다.

## 결정 요약

- `/read`의 콘텐츠 단위는 "요청 하나 + 그 요청에 달린 모든 답변"이며, 처음부터 전체를 항상 보여준다(요약 → 펼침 단계 없음).
- 별도 상세 route(`/read/[id]` 등)를 만들지 않는다. 모든 내용은 피드 카드 안에서 바로 읽힌다.
- 시각 문법은 `/answer`의 채팅 버블(요청 왼쪽, 답변 오른쪽)을 재사용하되, 입력창·스킵·보류 같은 답하기 전용 개념은 없는 **읽기 전용 미니 세션**이다.
- 답변마다 작성자가 다를 수 있으므로, 오른쪽에 정렬된 답변 버블도 각각 자신의 익명 라벨을 표시한다("오른쪽 = 나"가 아니라 "오른쪽 = 답변들").
- 답변은 오래된 순(대화가 진행된 순서)으로 위에서 아래로 쌓는다.
- 피드에 나열되는 요청 카드 자체는 최신 요청 순으로 정렬한다.
- 요청에 달린 (숨김 처리되지 않은) 답변이 하나도 없으면 그 요청은 피드에 나오지 않는다 — 아직 답이 없는 요청을 보여주는 건 `/answer`의 역할이다.
- 본인이 쓴 요청도 피드에 포함된다.
- `마음에 남기기`는 북마크(리본) 모양 아이콘을 쓴다. 좋아요/하트 모양은 쓰지 않는다(스펙 원문: "이건 좋아요가 아니다"). 아이콘만으로 오해되지 않도록 "마음에 남기기" 텍스트 라벨을 항상 아이콘과 함께 보여준다.
- `마음에 남기기`는 확인 다이얼로그 없이 즉시 토글된다 — 개인적이고 가역적인 저장 행동이라, `/answer`의 신고/스킵/보류처럼 되돌리기 어려운 조작과는 성격이 다르다고 판단했다.
- 신고는 요청과 답변 각각에 개별적으로 걸 수 있고, `/answer`와 동일하게 확인 다이얼로그를 거친 뒤 처리한다.
- 신고로 요청 또는 답변이 숨겨지면, 피드는 그 상태를 그대로 반영해 자동으로 갱신된다(답변이 전부 사라지면 카드 자체가 사라짐).

## 화면 구조

```text
[ 다른 요청 카드들 - 최신 요청 순, 위에서 아래로 ]

┌──────────────────────────────────────────┐
│ 익명 3                          🚩  8월 19일 09:00
│ 오늘 작은 실수를 계속 떠올리게 됩니다.
│
│                                    익명 7 🚩  8월 19일 09:20
│                              괜히 커 보일 때가 있죠.
│
│                                    익명 2 🚩  8월 19일 10:05
│                              저도 비슷한 적 있어요. 지나갔어요.
│
│ 🔖 마음에 남기기                                    │
└──────────────────────────────────────────┘

┌──────────────────────────────────────────┐
│ 익명 5                          🚩  8월 18일 20:00
│ 끝내긴 했는데 잘한 건지 모르겠어요.
│
│                                    익명 1 🚩  8월 18일 20:30
│                              괜히 커 보일 때가 있죠.
│
│ 🔖 마음에 남기기                                    │
└──────────────────────────────────────────┘
```

- 화면은 단일 컬럼이다. 데스크톱에서도 3컬럼 이상으로 쪼개지 않는다(원 스펙 요구사항). 폭은 `/login`·`/me` placeholder가 쓰던 읽기용 폭(`max-w-3xl`)을 따른다 — `/answer`의 넓은 채팅 폭(`max-w-6xl`)과는 다르다.
- 날짜 구분선(`/answer`의 `DateDivider`)은 쓰지 않는다. `/read`는 하나로 이어지는 대화 로그가 아니라 서로 독립된 요청 카드들의 피드이기 때문이다.

## 콘텐츠 단위 (카드) 구성

- **요청**: 작성자 익명 라벨, 작성 시각, 본문 전체, 신고 아이콘.
- **답변들**: 답변마다 작성자 익명 라벨, 작성 시각, 본문 전체, 신고 아이콘. 오래된 순으로 나열한다.
- **마음에 남기기**: 카드 전체(요청 기준)에 대해 하나. 북마크 아이콘 + 텍스트 라벨, 채워짐/비워짐으로 저장 여부를 표시한다. 공개 저장 수, 인기순, 랭킹은 만들지 않는다 — 저장 여부는 본인만 볼 수 있다.

## 마음에 남기기

- 좋아요가 아니다. 공개 인기 신호가 아니다. 나중에 다시 보고 싶은 온설을 개인적으로 저장하는 행동이다.
- 확인 없이 즉시 토글된다.
- 저장된 목록 자체를 `/read`에서 보여주지 않는다 — "마음에 남은 온설"은 `/me`에 둔다(`/me`는 이번 범위 밖).

## 신고

- 요청과 답변에 각각 독립적으로 건다. 확인 다이얼로그를 거친 뒤 처리한다(`reportRequest`/`reportReply` 재사용).
- 답변을 신고해서 그 요청의 마지막 남은 답변이 사라지면, 카드 전체가 피드에서 사라진다. 이건 별도 처리 코드가 필요한 게 아니라, 피드 계산이 매번 현재 상태에서 다시 계산되기 때문에 자연스럽게 일어난다.

## 후속 결정 필요

- `마음에 남긴 온설` 목록을 `/me`에서 어떻게 보여줄지 (이번 범위 밖).
- 피드가 아주 길어질 경우 페이지네이션/무한 스크롤이 필요한지 (현재 프로토타입 데이터 규모에서는 불필요, 전체를 한 번에 보여준다).

## 테스트 기준

`/read` 구현 시 최소한 아래를 검증한다.

- 답변이 하나도 없는 요청은 피드에 나오지 않는다.
- 본인이 쓴 요청도 피드에 나온다.
- 한 요청에 달린 여러 답변이 오래된 순으로 나온다.
- 요청 카드들은 최신 요청 순으로 나온다.
- 마음에 남기기를 누르면 확인 없이 즉시 토글되고, 새로고침(재하이드레이션) 후에도 유지된다.
- 요청/답변 각각을 신고하면 확인 다이얼로그를 거친 뒤 처리되고, 해당 항목이 화면에서 사라진다.
- 요청의 마지막 답변이 신고로 사라지면 카드 전체가 피드에서 사라진다.
- 데스크톱 폭에서도 피드는 1컬럼을 유지한다.
