# 온설 UX/IA 재설계 스펙

## 목적

localStorage 프로토타입은 요청 작성, 답변 작성, 최근 글, 내 활동이라는 핵심 기능이 한 브라우저 안에서 동작하는지 확인하기 위한 작업대였다. 다음 단계에서는 이 기능들을 한 화면에 모아둔 프로토타입 형태에서 벗어나, 사용자가 실제 서비스처럼 이해하고 이동할 수 있는 UX와 IA를 다시 잡는다.

이번 문서는 구현 전에 확정된 방향을 기록한다. 이후 구현 PR은 이 문서를 기준으로 작게 나누어 진행한다.

## 배경

현재 프로토타입의 문제는 기능 부족보다 방향성 부족에 가깝다.

- 요청 작성, 답변, 최근 글, 내 기록이 한 화면에 모여 있어 서비스의 중심 행동이 흐려진다.
- UI가 온설만의 제품 기준보다 생성형 AI 서비스의 기본 화면처럼 느껴진다.
- 답변 경험이 “무엇을 해야 하는지”는 보이지만 “어떤 태도로 말하면 되는지”를 자연스럽게 배우기 어렵다.
- 최근 글은 단순 예시뿐 아니라, 다른 사람의 사연과 답변을 읽으며 공감하는 소비형 경험이 될 수 있다.

따라서 프로토타입의 상태 모델과 localStorage 흐름은 재사용 후보로 남기되, 화면 구조와 시각 방향은 재설계한다.

## 재설계 원칙

### 오늘 남기기를 먼저 둔다

온설의 첫 행동은 오늘 힘들었던 일, 칭찬받고 싶은 일, 위로받고 싶은 일을 짧게 남기는 것이다. 첫 앱 화면은 사용자가 “바로 한마디 남겨도 되겠다”고 느끼게 해야 한다.

### 답하기로 쉽게 넘어갈 수 있게 한다

막연히 자기 이야기를 쓰는 일이 부담스러운 사용자가 있다. 이 사용자는 누군가의 글에 짧게 답하며 서비스를 이해할 수 있어야 한다.

### 읽는 경험을 별도 가치로 인정한다

온설 읽기는 단순한 샘플 목록이 아니다. 다른 사람의 사연과 담백한 답변을 읽으며 공감, 연민, 안도감을 느끼는 경험도 서비스의 중요한 가치다.

### 경쟁 신호를 만들지 않는다

초기 온설은 인기글, 랭킹, 좋아요 수, 공개 하트 수를 만들지 않는다. 좋은 글과 좋은 답변을 모으는 시도는 가능하지만, 사용자에게 경쟁처럼 보이지 않게 다룬다.

### 웹과 앱이 이어질 수 있게 이름을 고정한다

웹에서 사용하는 핵심 메뉴 이름은 나중에 앱 하단 탭이나 앱 내비게이션으로 옮겨도 어색하지 않아야 한다. 같은 개념은 같은 이름을 쓴다.

## 최종 IA

### 주요 내비게이션

주요 내비게이션은 사용자의 핵심 행동만 담는다.

- `남기기` -> `/today`
- `답하기` -> `/answer`
- `온설 읽기` -> `/read`

### 개인 영역

개인 영역은 상단 우측에 별도로 둔다.

- `내 기록` -> `/me`

`내 기록`은 사실상 내 정보에 해당하므로 주요 내비게이션에 넣지 않는다. 설정, 프로필, 닉네임, 알림은 후순위다.

### 제외 또는 후순위

Footer는 이번 핵심 UX/IA 범위에서 제외한다. 나중에 서비스 소개, 이용약관, 개인정보처리방침, 신고/운영 정책, 문의, 앱 다운로드 또는 웹/앱 선택 안내가 필요해질 때 추가한다.

## `/today`: 남기기

### 역할

`/today`는 온설의 첫 앱 화면이다. 사용자는 이 화면에서 오늘 어떤 말을 듣고 싶은지 짧게 남긴다.

### 화면 구조

권장 순서:

1. 기본 문구
2. 순환하는 온설 문구
3. 요청 입력창과 보내기 버튼
4. 제출 상태 메시지
5. 작은 활동 문장

첫 화면은 ChatGPT 첫 화면처럼 핵심 기능만 단순하게 보여준다. 여러 섹션, 하단 카드 피드, 보조 링크를 함께 노출하지 않는다.

기본 문구:

```text
오늘 어떤 말을 듣고 싶나요?
```

초기 `/today`에서는 `누군가에게 답하기` 보조 링크를 입력창 근처에 두지 않는다. 답하기는 주요 내비게이션의 `답하기`에서 접근한다. 모바일에서 입력 주변이 과해지는 것을 피하고, 첫 화면의 핵심 행동을 `남기기`로 유지하기 위함이다.

### 순환하는 온설

입력창 위에는 최근에 올라온 다른 온설 1개를 보여준다. 이는 하단 카드 피드가 아니라, 핵심 입력 화면 안에서 짧게 지나가는 참고 온설이다.

데이터 기준:

- 최근 온설 캐시를 우선 사용한다.
- 최근 온설 캐시가 비어 있으면 기본 샘플을 fallback으로 보여준다.
- 내가 방금 작성한 온설은 순환 온설에 즉시 넣지 않는다.
- 내가 작성한 온설은 `/me`의 내 기록에서 확인한다.
- 내가 작성한 온설을 상기시키는 기능이 필요해지면 순환 온설이 아니라 별도 버튼 또는 펼침 UI로 다룬다.

목적:

- 사용자가 “이 정도로 짧게 남겨도 되는구나”를 느끼게 한다.
- 온설이 AI 프롬프트 입력기가 아니라 사람들의 짧은 고민이 오가는 서비스라는 점을 보여준다.
- 첫 화면이 비어 보이지 않게 하되, 입력 행동보다 강해지지 않게 한다.

예시 문장:

- 오늘 실수한 일이 계속 떠올라요.
- 별일 아닌데 마음이 좀 가라앉았어요.
- 끝내긴 했는데 잘한 건지 모르겠어요.
- 그냥 오늘 하루 버틴 걸 알아줬으면 해요.

동작 기준:

- 기본 전환 방식은 soft vertical wipe다.
- 전환 간격은 5초를 기본값으로 둔다.
- 전환 시간은 600ms를 기본값으로 둔다.
- easing은 `cubic-bezier(0.22, 1, 0.36, 1)` 또는 그에 가까운 ease-out 계열을 사용한다.
- 타이핑 애니메이션, 반짝임, chip 추천 UI는 사용하지 않는다.
- 사용자가 입력을 시작하면 순환 온설 전환을 멈춘다.
- `prefers-reduced-motion`에서는 wipe를 사용하지 않고 즉시 교체 또는 최소 fade로 대체한다.
- 초기 버전에서는 온설을 클릭해 자동 입력하지 않는다.
- 여러 최근 온설 카드를 하단에 늘어놓지 않는다. 읽기 피드는 `/read`에서 다룬다.

전환 방식, 전환 간격, 전환 시간은 나중에 앱 설정 또는 내 정보 설정에서 개인화할 수 있는 후보로 둔다. 초기 구현에서는 설정 UI를 만들지 않고, 상수 또는 작은 config 객체로 분리해 둔다.

### 입력 영역

입력 영역은 첫 화면의 핵심 기능을 직접 드러낸다.

```text
오늘 어떤 말을 듣고 싶나요?

별일 아닌데 마음이 좀 가라앉았어요.

[ 오늘 어떤 말을 듣고 싶나요?              ] [보내기]
```

초기 구현에서는 텍스트 입력과 보내기 버튼만 노출한다. 입력창은 한 줄 composer처럼 시작하지만 실제 구현은 textarea로 둔다. 입력이 길어지면 3-4줄까지 자연스럽게 커지고, 그 이상은 높이를 제한한다.

나중에 이미지 추가 같은 보조 행동이 들어갈 수 있도록 입력창 옆 액션 영역은 확장 가능하게 설계한다.

이미지 업로드는 후순위다. 초기 화면에 비활성 이미지 버튼을 미리 보여주지는 않는다.

### 제출 lifecycle

제출 흐름은 명확히 보이게 한다.

1. 사용자가 `보내기`를 누른다.
2. 입력창과 보내기 버튼이 pending 상태로 전환된다.
3. pending 중에는 중복 제출을 막는다.
4. 성공하면 `남겨졌어요` 상태 메시지를 보여준다.
5. 입력창을 비운다.
6. 화면 이동은 하지 않는다.

localStorage 프로토타입에서도 짧은 pending 상태를 둔다. 실제 서버가 없더라도 나중에 풀스택 전환 시 네트워크 지연, 중복 제출 방지, 실패 처리 UX가 자연스럽게 이어지게 하기 위함이다.

### 활동 문장

활동 정보는 서비스가 살아 있다는 힌트로만 사용한다.

예:

```text
오늘 12개의 이야기가 남겨졌고, 18개의 답장이 도착했어요.
```

숫자는 성과 지표처럼 강조하지 않는다.

## `/answer`: 답하기

### 역할

`/answer`는 답변이 필요한 글을 보고 짧게 답하는 화면이다. 한 요청만 크게 띄우는 상담 화면보다, 여러 사람의 요청과 내가 남긴 답변이 이어지는 일반 채팅방 형태에 가깝게 만든다.

### 화면 구조

답변 세션은 아래와 같은 흐름을 가진다.

```text
익명 1
오늘 실수한 일이 계속 떠올라요.

                                      괜히 커 보일 때가 있죠.
                                      그래도 오늘 바로 끝난 일로
                                      남겨도 될 것 같아요.

익명 2
끝내긴 했는데 잘한 건지 모르겠어요.

                                      그래도 끝까지 해낸 건
                                      분명히 남는다고 생각해요.
```

요청은 왼쪽에, 내가 남긴 답변은 오른쪽에 둔다. 요청 작성자에는 작은 프로필 표시와 이름 또는 익명 표시를 붙인다. 사용자가 답변을 제출하면 해당 요청과 내 답변은 화면에 남고, 다음 요청이 자연스럽게 이어진다.

이 화면은 챗봇 대화가 아니다. 시스템이나 AI가 사용자의 말에 답하는 구조로 보이지 않아야 한다. 왼쪽 메시지는 다른 사용자의 요청이고, 오른쪽 메시지는 현재 사용자의 답변이다.

### 요청 노출 기준

우선 노출 기준은 기존 프로토타입의 의도를 유지한다.

1. 오늘 올라온 요청
2. 답변이 적은 요청
3. 아직 답변받지 못한 요청
4. 최신 요청

한 사람은 한 위로 요청에 답변 1개만 남긴다. 이미 답변한 요청은 다시 답변할 수 없고, 세션 로그 안에서는 이전에 답변한 흐름으로만 남는다.

### 답변 보조 장치

답변에 익숙하지 않은 사용자를 위해 입력창 근처에 아주 짧은 기준을 둔다.

```text
정답을 쓰지 않아도 됩니다. 짧게 들었다는 말이면 충분해요.
```

답변 예시는 톤을 보여주는 정도로만 둔다.

```text
그 마음이 오래 남을 수 있죠. 그래도 오늘 버틴 건 분명해요.
```

보조 장치는 답변을 대신 써주는 느낌을 주면 안 된다. AI가 자동으로 문장을 생성하는 인터페이스처럼 보이지 않게 한다.

### 보조 행동

- `넘기기`
- `다른 글 보기`
- `신고`

넘기기와 다른 글 보기는 사용자가 답하기 어렵거나 불편한 글을 만났을 때 빠져나갈 수 있는 장치다.

## `/read`: 온설 읽기

### 역할

`/read`는 다른 사람의 요청과 답변을 읽는 화면이다. 처음 온 사용자가 온설의 문장 톤을 배우는 예시 역할도 하지만, 그 자체로 소비형 피드가 될 수 있다.

### 콘텐츠 단위

하나의 읽기 단위는 요청과 답변 묶음이다.

- 요청 본문
- 답변 일부 또는 대표 답변
- 작성 시각
- 신고 상태를 통과했다는 전제
- `마음에 남기기`

긴 내용은 일부만 보여주고, 상세 또는 펼침에서 전체를 읽게 한다.

### 마음에 남기기

`마음에 남기기`는 좋아요가 아니다. 공개 인기 신호도 아니다. 사용자가 나중에 다시 보고 싶은 온설을 개인적으로 저장하는 행동이다.

초기 화면에서는 저장 여부만 사용자가 알 수 있게 표시한다. 공개 저장 수, 인기순, 랭킹은 만들지 않는다.

## `/me`: 내 기록

### 역할

`/me`는 내가 온설에서 남긴 흔적을 다시 확인하는 개인 화면이다.

### 포함 범위

- 내가 남긴 요청
- 내가 남긴 답변
- 내가 마음에 남긴 온설

설정, 배경, 닉네임, 알림, 앱 연동은 후순위다.

### 접근 위치

`내 기록`은 상단 우측 개인 영역에 둔다. 주요 내비게이션의 `남기기`, `답하기`, `온설 읽기`와 같은 레벨로 두지 않는다.

## 시각 방향

### 목표

온설은 담백한 쪽지함과 조용한 채팅방 사이에 있다. 화면은 따뜻해야 하지만 과하게 감성적이면 안 된다. 사용자의 글이 중심이 되어야 하며, UI가 감정을 대신 연기하면 안 된다.

### 피해야 할 방향

- 생성형 AI 서비스처럼 보이는 큰 입력창과 추천 chip 묶음
- 보라색 또는 남색 gradient 중심의 화면
- 상담 챗봇처럼 보이는 assistant/user 대화 구조
- 감정 문구를 과장하는 hero 또는 카드
- 인기글, 랭킹, 공개 반응 수처럼 경쟁을 유도하는 장치

### 허용하는 방향

- 짧은 쪽지와 답장을 읽기 좋게 보여주는 단정한 레이아웃
- 라이트/다크 모두에서 낮은 눈부심과 충분한 대비를 가진 색상
- 채팅방처럼 익숙하지만, “AI와 대화”가 아니라 “사람의 요청에 사람이 답하는” 구조가 드러나는 화면
- 숫자는 작은 활동 힌트로만 사용

## 반응형 기준

공통 기준은 `docs/design/06-responsive-layout.md`를 따른다. 이번 UX/IA에서는 route별 적용 방식을 아래처럼 둔다.

### 모바일

- `/today`: 작성 흐름을 첫 화면 최상단에 둔다.
- `/answer`: 채팅 로그와 입력창을 1컬럼으로 둔다. 입력창이 콘텐츠를 계속 가리지 않게 한다.
- `/read`: 요청+답변 묶음을 세로 피드로 읽게 한다.
- `/me`: 세 목록을 탭 또는 단순 섹션으로 나눌 수 있다.

### 태블릿

- 세로 태블릿은 모바일 확장으로 본다.
- `/answer`는 로그 폭을 너무 넓히지 않고 읽기 폭을 제한한다.
- `/read`는 1컬럼을 기본으로 하되, 미리보기 밀도를 조금 높일 수 있다.

### 데스크톱

- `/today`: 기본 문구, 순환 온설 문구, 입력창만 중앙에 둔다. 여러 미리보기 카드를 하단에 늘어놓지 않는다.
- `/answer`: 왼쪽 보조 영역 없이도 채팅 로그 중심으로 충분하다. 필요하면 오른쪽에 답변 가이드나 이전 예시를 작은 보조 영역으로 둘 수 있다.
- `/read`: 넓은 화면을 채우기 위해 3컬럼 이상으로 쪼개지 않는다.
- `/me`: 목록 비교가 필요하면 2컬럼까지 허용한다.

## 구현 PR 분리

구현은 한 PR에 모두 넣지 않는다.

권장 순서:

1. `/today` 남기기 화면 재설계
2. `/answer` 채팅방형 답변 세션
3. `/read` 온설 읽기 화면
4. `/me` 내 기록 화면

각 PR은 localStorage 프로토타입의 기존 데이터 흐름을 가능한 한 유지하되, UI와 route 책임을 작게 나누어 변경한다.

## 결정된 사항

- 첫 앱 화면은 `/today`이며 `남기기`로 표시한다.
- `/today`는 기본 문구, 순환 온설 문구, 입력창, 보내기 버튼을 중심으로 구성한다.
- `/today` 순환 온설은 최근 온설 캐시를 우선 사용하고, 없으면 기본 샘플을 fallback으로 보여준다.
- `/today` 순환 온설은 soft vertical wipe로 전환한다.
- `/today` 제출은 pending, 성공, `남겨졌어요`, 입력창 비움 lifecycle을 명확히 보여준다.
- `/today`에는 초기 범위에서 `누군가에게 답하기` 보조 링크를 두지 않는다.
- 주요 내비게이션은 `남기기`, `답하기`, `온설 읽기`다.
- `내 기록`은 상단 우측 개인 영역으로 분리한다.
- `/answer`는 한 요청만 고립해서 보여주는 화면이 아니라, 여러 요청과 내 답변이 이어지는 채팅방형 세션이다.
- `/read`는 최근 온설을 읽는 소비형 피드다.
- `마음에 남은 온설`은 `/read` 탭이 아니라 `/me`에 둔다.
- `마음에 남기기`는 개인 저장 행동이며 공개 좋아요나 랭킹이 아니다.
- Footer는 이번 구현 범위에서 제외하고 후순위로 둔다.

## 후속 결정 필요

아래 항목은 구현 전에 별도 확인이 필요하다.

- `/answer`에서 답변 입력창을 하단 고정으로 둘지, 로그 아래 자연 배치로 둘지
- `/read`에서 요청+답변 묶음의 상세 화면을 별도 route로 둘지, 펼침으로 처리할지
- `마음에 남기기`의 시각 표현을 bookmark, pin, save 중 어떤 상징으로 잡을지
- 로그인 전 localStorage draft를 route별로 어떻게 안내할지
- 신고/필터 안내를 어느 시점에 얼마나 노출할지

## 위키 기록 후보

이 문서는 위키 모드에서 바로 옮겨 적기 위한 원문이 아니라, 이후 위키 에이전트가 프로젝트 지식으로 승격할 수 있도록 결정과 맥락을 누락 없이 모은 작업 기록이다.

위키로 승격할 때 중요한 지식:

- 프로토타입은 기능 흐름 검증용이고 최종 UX 방향은 아니다.
- 온설의 핵심 IA는 `남기기`, `답하기`, `온설 읽기`, `내 기록`으로 분리한다.
- 답변 화면은 챗봇이 아니라 사람 간 채팅방형 답변 세션이다.
- 읽기 경험은 예시 목록이 아니라 공감과 톤 학습을 제공하는 별도 가치다.
- 공개 경쟁 신호를 피하고, 개인 저장인 `마음에 남기기`만 초기 범위에 둔다.
