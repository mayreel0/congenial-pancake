# 온설 localStorage 앱 프로토타입 설계

## 목적

이번 단계는 풀스택 MVP가 아니라, 온설의 핵심 사용 흐름을 웹에서 빠르게 만져볼 수 있는 localStorage 기반 프로토타입을 만든다.

프로토타입의 목표는 서비스 판단을 완전히 검증하는 것이 아니다. 요청 작성, 답변 작성, 답변 부족 요청 우선 노출, 내 활동 확인이 한 화면 흐름 안에서 자연스러운지 보고, 이후 Storybook으로 분리할 실제 컴포넌트 후보를 찾는 것이다.

## 방향 결정

- 프로토타입을 먼저 만든 뒤 Storybook을 도입한다.
- Storybook은 프로토타입에서 실제로 쓰인 컴포넌트를 분리해 확인하는 단계로 둔다.
- 이번 프로토타입은 인증, 서버, 데이터베이스, AI 필터, 앱 알림을 만들지 않는다.
- 구현 전 route와 범위는 다시 사용자 확인을 받는다.

## 추천 route

추천 route는 `/today`다.

이유:

- 사용자가 “오늘 있었던 일”을 남긴다는 핵심 상황과 맞다.
- `/app`보다 사용자 언어에 가깝다.
- 나중에 앱으로 확장해도 “오늘” 탭 또는 첫 화면 개념으로 이어갈 수 있다.

구현 전 확인할 결정:

- `/today`를 프로토타입 route로 확정할지
- 랜딩의 `웹에서 시작하기` 버튼을 `/today`로 연결할지

## 포함 범위

### 1. 위로 요청 작성

로그인 전 사용자처럼 작성할 수 있어야 한다.

- 사용자는 짧은 위로 요청을 작성한다.
- 제출 전 draft는 localStorage에 저장된다.
- 제출하면 localStorage의 요청 목록에 추가된다.
- 제출 후 draft는 비워진다.

프로토타입에서는 실제 로그인 흐름을 만들지 않는다. “로그인 후 이어서 제출 가능”이라는 MVP 요구사항은 draft persistence와 pending 상태로만 표현한다.

### 2. 답변 작성

사용자는 다른 사람의 위로 요청에 답변할 수 있다.

- 한 요청에는 여러 답변이 달릴 수 있다.
- 현재 브라우저 사용자는 같은 요청에 답변 1개만 남길 수 있다.
- 제출 전 답변 draft는 요청별로 localStorage에 저장된다.
- 답변 제출 후 draft는 비워진다.

프로토타입에서는 사용자 계정을 만들지 않는다. 현재 브라우저를 하나의 임시 사용자로 본다.

### 3. 답변 부족 요청 우선 노출

요청 목록은 아래 기준으로 정렬한다.

1. 오늘 올라온 요청
2. 답변 수가 적은 요청
3. 답변이 없는 요청
4. 최신 요청

프로토타입에서는 “오늘” 판정을 브라우저의 현재 날짜 기준으로 단순 처리한다.

### 4. 최근 위로/답변 섹션

처음 온 사용자가 어떻게 쓰면 되는지 감을 잡을 수 있게 최근 요청과 답변을 보여준다.

- 실제 localStorage 데이터 기반으로 표시한다.
- 요청과 답변 preview는 너무 길면 일부만 보여준다.
- 신고로 숨김 처리된 항목은 표시하지 않는다.

### 5. 신고/필터 stub

프로토타입은 실제 안전 필터를 만들지 않는다.

대신 아래 UI 상태만 둔다.

- 요청 신고 버튼
- 답변 신고 버튼
- 신고 후 localStorage에서 숨김 처리
- 무성의하거나 공격적인 문구에 대한 간단한 client-side 경고 후보

이 단계에서 AI 자동 댓글은 만들지 않는다.

### 6. 내 정보

간단한 내 활동 영역을 둔다.

- 내가 쓴 위로 요청 목록
- 내가 남긴 답변 목록

닉네임, 배경, 설정은 후순위다.

## 제외 범위

- 실제 회원가입과 로그인
- Nest.js 백엔드
- 데이터베이스
- 서버 기반 중복 신고 처리
- 실제 AI 안전 필터
- 자동 댓글 생성
- 앱 알림
- 시즌 이벤트
- 오늘의 온기/화로 같은 활동 시각화

## 데이터 모델

프로토타입 데이터는 localStorage에 저장한다.

추천 key:

- `onseol.prototype.requests`
- `onseol.prototype.replyDrafts`
- `onseol.prototype.requestDraft`
- `onseol.prototype.viewer`

### Request

```ts
type Request = {
  id: string;
  body: string;
  createdAt: string;
  authorId: string;
  replyIds: string[];
  reportCount: number;
  hidden: boolean;
};
```

### Reply

```ts
type Reply = {
  id: string;
  requestId: string;
  body: string;
  createdAt: string;
  authorId: string;
  reportCount: number;
  hidden: boolean;
};
```

### Viewer

```ts
type Viewer = {
  id: string;
};
```

프로토타입에서는 `viewer.id`를 최초 접속 시 localStorage에 생성한다. 이 값은 실제 계정이 아니라 현재 브라우저 사용자 식별용이다.

## 화면 구조

### 모바일

모바일은 1컬럼을 기본으로 한다.

권장 순서:

1. 오늘 남기기 composer
2. 답변을 기다리는 요청
3. 최근 위로/답변
4. 내 활동

모바일에서는 작성 흐름이 가장 먼저 보여야 한다. 답변 부족 요청은 그 다음 우선순위다.

### 태블릿

태블릿은 1컬럼을 기본으로 하되, 여유가 있으면 요청 목록과 선택된 요청을 느슨하게 분리할 수 있다.

구현 복잡도를 줄이기 위해 첫 프로토타입에서는 태블릿도 모바일 확장형 1컬럼을 기본 추천한다.

### 데스크톱

데스크톱은 2영역 구성을 추천한다.

- 왼쪽: 작성 composer와 우선 노출 요청 목록
- 오른쪽: 선택된 요청, 답변 목록, 답변 composer, 내 활동 요약

단, 첫 구현에서 상태가 복잡해지면 데스크톱도 단일 흐름 레이아웃으로 시작한다. 프로토타입의 목적은 고급 레이아웃보다 핵심 흐름 확인이다.

## 컴포넌트 후보

프로토타입 구현 후 Storybook으로 분리할 후보는 아래와 같다.

- `RequestComposer`
- `ReplyComposer`
- `NoteCard`
- `ReplyCard`
- `ActivitySummary`
- `RecentExchangeList`
- `MyActivityList`
- `ReportButton`

각 컴포넌트는 긴 한국어 문장, 빈 상태, 신고 숨김 상태, 다크모드 상태를 story로 확인할 수 있어야 한다.

## 상태 흐름

### 요청 작성

1. 사용자가 요청을 입력한다.
2. 입력값을 `onseol.prototype.requestDraft`에 저장한다.
3. 제출하면 `Request`를 생성한다.
4. 요청 목록에 추가한다.
5. draft를 비운다.

### 답변 작성

1. 사용자가 요청을 선택한다.
2. 답변을 입력한다.
3. 요청별 draft를 `onseol.prototype.replyDrafts`에 저장한다.
4. 이미 답변한 요청이면 제출을 막는다.
5. 제출하면 `Reply`를 생성하고 요청의 `replyIds`에 연결한다.
6. 해당 요청의 답변 draft를 비운다.

### 신고 처리

1. 사용자가 요청 또는 답변을 신고한다.
2. 해당 항목의 `reportCount`를 올린다.
3. 프로토타입에서는 신고 즉시 `hidden: true`로 둘 수 있다.
4. 숨김 항목은 최근 섹션과 우선 노출 목록에서 제외한다.

중복 신고 처리는 풀스택 MVP에서 서버 기준으로 다시 설계한다.

## 빈 상태와 샘플 데이터

프로토타입 첫 접속 시 빈 화면이 너무 차갑게 보이면 안 된다.

추천:

- 초기 샘플 요청 2개
- 초기 샘플 답변 2개
- 사용자가 첫 제출을 하면 샘플과 사용자 데이터를 함께 보여준다.
- 샘플 데이터는 프로토타입 초기화 버튼으로 다시 만들 수 있다.

구현 전 확인할 결정:

- 샘플 데이터를 자동으로 넣을지
- “데이터 초기화” 버튼을 화면에 노출할지, 개발용으로만 둘지

## 디자인 적용 기준

프로토타입도 디자인 시스템을 따른다.

- 생성형 SaaS 랜딩처럼 보이는 hero, gradient, 카드 3개 패턴을 피한다.
- 사용자의 요청과 답장이 가장 먼저 읽혀야 한다.
- 숫자는 성과 지표처럼 보이지 않게 작게 쓴다.
- 카드 안에 카드가 중첩된 것처럼 보이는 구조를 피한다.
- 라이트/다크 모드를 함께 확인한다.
- 모바일 390px에서 줄바꿈과 터치 타겟을 확인한다.

## 웹/앱 일관성

프로토타입은 웹에서 만들지만 앱 확장을 고려한다.

- 기능 이름은 앱에서도 쓸 수 있는 말로 둔다.
- request, reply, draft, hidden 같은 상태 의미는 웹/앱 공통 개념으로 둔다.
- 앱 알림은 만들지 않지만 “답장 도착”이 앱에서 중요해질 수 있음을 기록한다.
- 웹의 route와 앱의 tab/stack navigation은 달라도 핵심 흐름 순서는 유지한다.

## 검증 계획

구현 PR에서 확인할 항목:

- `pnpm lint`
- `pnpm typecheck`
- `pnpm build`
- localStorage draft 저장과 복원
- 요청 제출 후 목록 반영
- 답변 제출 후 요청 상세 반영
- 같은 요청에 중복 답변 방지
- 신고 후 최근/우선 목록에서 숨김
- 모바일 390px, 태블릿 768px, 데스크톱 1024px, 넓은 데스크톱 1440px 확인
- 라이트/다크 모드 확인

## Storybook 전환 기준

프로토타입 리뷰 후 아래 조건을 만족하면 Storybook 도입 PR로 넘어간다.

- 반복되는 컴포넌트 후보가 4개 이상 확인된다.
- 긴 한국어 텍스트, 빈 상태, 숨김 상태, 작성 중 상태를 따로 봐야 한다.
- 디자인 시스템과 어긋난 패턴을 컴포넌트 단위로 고쳐야 한다.

Storybook 도입 후에는 프로토타입에서 쓰던 컴포넌트를 story로 분리하고, 다시 앱 화면에 반영한다.

## 구현 전 확인할 결정 목록

- route를 `/today`로 확정할지
- 랜딩의 `웹에서 시작하기`를 `/today`로 연결할지
- 초기 샘플 데이터를 자동 삽입할지
- 데이터 초기화 버튼을 사용자 화면에 노출할지
- 데스크톱을 2영역 구성으로 시작할지, 단일 흐름으로 시작할지
- 신고 즉시 숨김 처리를 적용할지, 신고 count만 보여줄지
