# 온설 답하기 세션 스펙

## 목적

`docs/superpowers/specs/2026-08-17-onseol-ux-ia-redesign.md`는 `/answer`를 "여러 요청과 내 답변이 이어지는 채팅방형 세션"으로 정의했지만, 요청 카드의 실제 구성과 `넘기기`/`다른 글 보기`/`신고` 같은 보조 행동의 세부 동작은 후속 결정으로 남겨두었다. 이 문서는 그 후속 결정을 확정하고, `/answer` 구현 계획(plan)을 쓰기 전에 필요한 화면·상태 규칙을 정리한다.

이 문서는 `/today`의 localStorage 프로토타입 상태 모델과 기존 컴포넌트(`NoteCard`, `ReplyCard`, `ReplyComposer`, `ReportButton`, `useOnseolPrototype`, `model.ts`)를 재사용 후보로 전제한다.

## 배경

- 2026-08-17 UX/IA 재설계 문서는 `/answer`를 한 요청만 고립해서 보여주는 화면이 아니라 채팅방형 세션으로 정의했고, 보조 행동으로 `넘기기`, `다른 글 보기`, `신고`를 나열했다.
- 그 문서의 "후속 결정 필요" 항목 중 아래 두 가지가 이 문서에서 해소된다.
  - `/answer`에서 답변 입력창을 하단 고정으로 둘지, 로그 아래 자연 배치로 둘지 → 하단 고정으로 확정.
  - 신고/필터 안내를 어느 시점에 얼마나 노출할지의 일부(신고와 스킵의 관계) → 신고 시 스킵도 함께 처리하는 것으로 확정.
- 논의 과정에서 `넘기기`와 `다른 글 보기`가 같은 동작이었음을 확인했고, `보류`라는 새 개념이 추가로 필요해졌다.

## 결정 요약

- `/answer`는 요청(왼쪽)-내 답변(오른쪽)이 아래에서 위로 쌓이는 채팅방형 로그다.
- 입력창은 하단 고정이다.
- 로그를 위로 스크롤하면 이전에 완료한 요청/답변이 계속 이어져 보인다(append-only 히스토리).
- 요청 카드에는 신고와 스킵 버튼이 있다.
- `넘기기`, `다른 글 보기`는 `스킵`과 동일한 동작이며 별도로 구분하지 않는다.
- 신고하면 해당 요청은 스킵도 함께 처리된다.
- 스킵한 요청은 보류함에 없으면 내 답하기 큐에서 영구히 빠진다.
- `보류`는 스킵과 달리 요청을 따로 보관해 나중에 답할 수 있게 한다.
- 보류함은 `/answer` 화면 안에서 연다.
- 보류 중인 요청에 답하면, 그 요청+답변 쌍은 "지금 답변을 완료한 시점" 기준으로 로그 맨 아래에 새로 합류한다.
- 본인이 작성한 요청은 답하기 큐에 노출되지 않는다.

## 화면 구조

```text
[ 이전 요청/답변 히스토리 - 스크롤로 올라가며 계속 이어짐 ]

익명 1                                  · 8월 19일 14:02
오늘 실수한 일이 계속 떠올라요.        신고 · 스킵

                                      괜히 커 보일 때가 있죠.
                                      그래도 오늘 바로 끝난 일로
                                      남겨도 될 것 같아요.

익명 2                                  · 8월 19일 14:05
끝내긴 했는데 잘한 건지 모르겠어요.    신고 · 스킵

--------------------------------------------------
[ 보류 중 (2) ]                    [ 입력창                    ] [보내기]
```

- 요청은 왼쪽, 내 답변은 오른쪽에 정렬한다.
- 이미 답변을 완료한 요청 카드에는 신고/스킵 버튼을 남겨두지 않는다(완료된 항목은 더 이상 큐 대상이 아니므로).
- 아직 답변하지 않은, 현재 응답 대상 요청 카드에만 신고/스킵 버튼이 보인다.

## 요청 카드 구성

- **요청자**: 익명 표시(예: `익명 1`). 실제 계정/닉네임 체계는 인증 스펙에서 다룬다.
- **요청글**: 본문. 같은 줄 또는 바로 옆에 `신고`, `스킵` 버튼을 둔다.
- **작성 날짜 및 시간**: 요청이 처음 작성된 시각을 표시한다(응답 완료 시각이 아니라 원 작성 시각).

## 보조 행동

### 신고

- 신고하면 해당 요청은 즉시 숨김 처리되고(`reportCount` 증가, `hidden: true`) 큐에서 사라진다.
- 신고와 동시에 스킵도 함께 이루어진다. 즉 신고 후 별도로 스킵을 다시 누를 필요가 없다.
- 신고된 요청은 보류함으로 보낼 수 없다.

### 스킵 (= 넘기기 = 다른 글 보기)

- 스킵하면 해당 요청은 현재 세션에서 사라지고, 이후에도 내 답하기 큐에 다시 나타나지 않는다(영구 제외, 세션 한정 아님).
- 스킵은 신고와 달리 요청 자체를 숨기지 않는다. 다른 사용자의 큐에는 그대로 노출된다.
- 스킵 여부는 사용자별로 관리한다(내가 스킵해도 다른 사람 큐에는 영향 없음).

### 보류

- 보류하면 해당 요청은 현재 세션에서 사라지지만, 스킵과 달리 보류함에 보관되어 나중에 다시 꺼내 답할 수 있다.
- 보류도 스킵처럼 라이브 답하기 큐에서는 빠진다(같은 글이 큐와 보류함에 동시에 존재하지 않는다).
- 보류 항목은 `/answer` 화면 안의 `보류 중 (N)` 진입점을 통해 목록으로 확인한다.

## 보류함과 라이브 큐의 관계

- 보류함에서 항목을 선택하면, 그 요청이 지금 답할 대상으로 전환되고 같은 하단 입력창을 사용해 답한다.
- 보류 항목에 답하는 동안에도 라이브 큐(다음 미답변 요청)는 그대로 유지된다. 보류 답변 작성이 라이브 큐를 대체하거나 초기화하지 않는다.
- 보류 항목에 답을 완료하면 보류함에서 제거되고, 그 요청+답변 쌍이 로그 맨 아래에 새 항목으로 합류한다.
- 로그 정렬 기준은 "요청이 노출된 시점"이 아니라 **"내가 답변을 완료한 시점"**이다. 며칠 전에 보류한 글이라도 방금 답했다면 로그 맨 아래(최신)에 붙는다. 이 규칙 덕분에 보류 답변이 과거 시점의 로그 중간에 끼어들어 타임라인이 꼬이는 문제가 생기지 않는다.

## 큐 노출 기준

기존 프로토타입 우선순위 로직(`getPriorityRequests`)을 유지하되 아래 필터를 추가한다.

1. 오늘 올라온 요청
2. 답변이 적은 요청
3. 아직 답변받지 못한 요청
4. 최신 요청
5. (추가) 본인이 작성한 요청 제외
6. (추가) 이미 답변한 요청 제외 — 기존 `hasViewerReplied`로 판단
7. (추가) 스킵한 요청 제외
8. (추가) 보류 중인 요청 제외 (보류함에서만 접근)

## 데이터 관점

구현 계획에서 다룰 상태 확장 후보(이 문서는 확정된 필드명을 강제하지 않는다):

- 사용자별 스킵한 요청 id 목록
- 사용자별 보류한 요청 id 목록과, 보류한 시각(정렬용)
- 요청+답변 로그의 정렬 키로 쓸 "답변 완료 시각" (기존 `reply.createdAt`을 그대로 정렬 기준으로 써도 되는지, 아니면 별도 필드가 필요한지는 구현 계획에서 결정)
- 기존 `PrototypeState`/`storage.ts` 패턴을 따라 스킵/보류 목록도 localStorage에 viewer 단위로 영속 저장한다(기존 요청/답변/드래프트와 동일한 저장 방식).

## 결정된 사항

- `/answer`는 요청 왼쪽, 내 답변 오른쪽, 하단 고정 입력창을 가진 채팅방형 세션이다.
- 로그는 위로 스크롤하면 이전 완료 항목이 계속 이어지는 append-only 히스토리다.
- 요청 카드는 요청자, 요청글+신고/스킵, 작성 날짜·시간으로 구성한다.
- `넘기기`와 `다른 글 보기`는 `스킵`과 같은 동작이다.
- 신고하면 스킵도 함께 처리된다.
- 스킵한 요청은 내 큐에서 영구 제외된다.
- 보류는 스킵과 달리 나중에 다시 꺼내 답할 수 있도록 별도 보관한다.
- 보류함은 `/answer` 화면 안에 둔다.
- 보류 항목에 대한 답변은 완료 시점 기준으로 로그 맨 아래에 합류한다.
- 본인이 작성한 요청은 답하기 큐에 노출되지 않는다.

## 후속 결정 필요

- 보류함 목록의 정렬 기준(보류한 순서 vs 원 요청 우선순위 vs 원 요청 작성 시각).
- 보류 항목 개수 제한 여부(무제한으로 계속 쌓일 수 있게 둘지, 상한을 둘지).
- 보류가 만료되는지(예: 원 요청에 다른 사용자가 이미 답변을 채워 더 이상 답이 필요 없어지면 보류함에서 자동으로 사라지는지).
- 신고 시 확인 다이얼로그 없이 즉시 처리할지, 짧은 확인 단계를 둘지.
- 스킵/보류 상태를 `/me`(내 기록)에서도 노출할지, `/answer` 내부 상태로만 둘지.
- 로그인 전 비회원 상태에서도 스킵/보류 상태를 localStorage로 유지할지, 보류는 로그인 사용자만 쓸 수 있게 제한할지.

## 테스트 기준

`/answer` 구현 시 최소한 아래를 검증한다.

- 요청 카드에 요청자, 본문, 신고/스킵 버튼, 작성 시각이 보인다.
- 신고를 누르면 해당 요청이 큐와 화면에서 사라지고 다시 노출되지 않는다.
- 스킵을 누르면 해당 요청이 큐에서 사라지고, 이후 큐 재계산에서도 다시 나타나지 않는다.
- 보류를 누르면 해당 요청이 큐에서 사라지고 보류함 목록에 나타난다.
- 보류함에서 항목을 선택해 답하면, 그 요청+답변이 보류함에서 제거되고 로그 맨 아래에 나타난다.
- 보류 답변을 작성하는 동안에도 원래 라이브 큐의 다음 요청이 유지된다.
- 본인이 작성한 요청은 큐에 노출되지 않는다.
- 로그를 위로 스크롤하면 이전에 완료한 요청/답변이 계속 보인다.
