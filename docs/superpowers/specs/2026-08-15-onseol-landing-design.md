# Onseol Landing Prototype Design

## Context

온설은 사용자가 오늘 힘들었던 일, 칭찬받고 싶은 일, 위로받고 싶은 일을 짧게 남기고 다른 사용자가 담백한 답장을 남기는 서비스다.
현재 저장소에는 제품 결정 문서만 있고 앱 코드는 없다.
첫 구현은 전체 localStorage 프로토타입을 한 번에 만들지 않고, 정적 랜딩 페이지부터 만든다.

이 선택은 구현을 늦추기 위한 것이 아니다.
랜딩과 실제 사용 화면의 책임을 처음부터 나누어 두면, 이후 요청 작성, 답변 작성, localStorage, 로그인 시뮬레이션을 붙일 때 라우트와 상태 경계를 다시 뜯지 않아도 된다.

## Goals

- 첫 방문자가 10초 안에 "짧게 남기면 누군가 담백하게 답해주는 서비스"임을 이해한다.
- 온설의 이름과 보조 문구인 "정답고 따뜻하게 나누는 이야기"가 첫 화면에서 분명하게 보인다.
- 랜딩이 비어 보이지 않도록 작은 활동 지표와 요청/답변 맛보기를 보여준다.
- 다음 PR에서 앱 본문 화면을 붙일 수 있도록 랜딩을 표시 전용 경계로 유지한다.

## Non-Goals

- 첫 PR에서 위로 요청 작성, 답변 작성, 로그인 시뮬레이션을 구현하지 않는다.
- 첫 PR에서 localStorage 저장, 신고 상태, 내 활동 화면을 구현하지 않는다.
- 첫 PR에서 실제 인증, 백엔드, 데이터베이스, AI 필터, 앱 설치 흐름을 구현하지 않는다.
- 첫 PR에서 MVP의 Nest.js 백엔드 구조를 만들지 않는다.

## Route Design

### First PR

- `/`: 정적 랜딩 페이지.

랜딩은 서비스 진입면이다.
이 페이지는 제품 설명, 활동 느낌, 웹 진입 버튼, 앱 준비 중 버튼을 보여준다.
데이터를 저장하거나 사용자 입력을 처리하지 않는다.

### Next PR Candidate

- `/today`: localStorage 기반 프로토타입 본문 후보 route.

`/app`은 구현자 관점의 이름이라 사용자의 서비스 맥락과 잘 맞지 않는다.
`/today`는 "오늘 있었던 일"을 남긴다는 핵심 사용 상황과 맞고 짧다.
다만 `/today`는 아직 확정 route가 아니라 다음 앱 화면 구현 전에 다시 확인할 후보로 둔다.

## Landing Content

랜딩은 짧게 유지한다.
긴 마케팅 페이지가 아니라 온설의 사용감을 얼핏 보여주는 첫 화면이다.

포함할 요소:

- 브랜드 이름: 온설
- 보조 문구: 정답고 따뜻하게 나누는 이야기
- 짧은 설명: 오늘 힘들었던 일이나 칭찬받고 싶은 일을 짧게 남기면, 누군가 담백하게 답장을 남기는 공간
- 주요 버튼: 웹에서 시작하기
- 보조 버튼: 앱으로 이용하기, 준비 중 상태
- 작은 활동 지표: 오늘의 위로 요청 수, 오늘의 답변 수, 답변을 기다리는 글 수
- 맛보기 카드: 짧은 위로 요청 1개와 현실적이고 담백한 답변 1개

## Interaction Design

첫 PR의 상호작용은 의도적으로 작게 둔다.

- `웹에서 시작하기`는 다음 본문 route 후보인 `/today`로 향하는 링크로 둘 수 있다.
- `/today`가 아직 구현되지 않은 경우, 링크는 비활성 또는 준비 중 상태로 표현한다.
- `앱으로 이용하기`는 준비 중 상태로 보이고 실제 앱 설치 플로우로 연결하지 않는다.
- 랜딩의 지표와 맛보기 문구는 정적 샘플 데이터다.

구현 단계에서 `웹에서 시작하기`를 실제 링크로 둘지, 준비 중 버튼으로 둘지는 구현 전 한 번 더 확인한다.
이 결정은 첫 PR의 사용자 기대와 관련된 UX tradeoff이기 때문이다.
현재 추천안은 첫 PR에서 `/today`를 만들지 않는다면 `웹에서 시작하기`도 준비 중 상태로 두는 것이다.

## State Boundary

첫 PR의 랜딩은 React state나 localStorage에 의존하지 않는다.
활동 지표와 맛보기는 정적 데이터로 둔다.

다음 PR에서 추가될 앱 본문은 별도 route와 별도 상태 모듈을 사용한다.
예상되는 다음 상태 경계:

- 위로 요청 draft
- 답변 draft
- 로그인 전 pending submit
- localStorage persistence
- 신고/숨김 UI 상태
- 내 요청과 내 답변 목록

이 상태들은 랜딩 컴포넌트로 흘러들어오지 않는다.
나중에 실제 데이터 기반 최근 섹션이 필요해지면, 랜딩은 별도 read-only summary 데이터만 받는다.

## Visual Direction

온설은 과하게 감성적이거나 AI스럽지 않은 담백한 위로를 지향한다.
랜딩도 같은 톤을 따른다.

- 화면은 조용하고 부드럽되 너무 비어 보이지 않게 구성한다.
- 큰 마케팅 hero보다 첫 화면 안에서 서비스 이름, 설명, 작은 지표, 맛보기 대화가 함께 보이게 한다.
- 카드와 버튼은 단정하게 사용한다.
- 문구는 과장된 감성어보다 현실적인 말투를 사용한다.

## Component Shape

첫 PR에서 예상되는 UI 단위:

- `LandingPage`
- `LandingHero`
- `ActivityStats`
- `SampleExchange`
- `EntryActions`

컴포넌트 이름은 구현 중 프레임워크 구조에 맞게 조정할 수 있다.
단, 랜딩 표시 컴포넌트와 다음 PR의 앱 상태 컴포넌트는 섞지 않는다.

## Error Handling

첫 PR은 정적 랜딩이므로 런타임 오류 흐름이 거의 없다.
대신 다음을 확인한다.

- 모바일 폭에서도 문구가 버튼과 카드 밖으로 넘치지 않는다.
- 준비 중 버튼은 실제 동작처럼 오해되지 않는다.
- 아직 구현되지 않은 route로 이동할 수 있는 링크는 사용자 기대를 해치지 않게 처리한다.

## Testing And Verification

첫 PR에서 확인할 항목:

- 앱이 로컬 dev server에서 렌더링된다.
- `/`에서 온설 브랜드, 보조 문구, 설명, 두 CTA, 활동 지표, 맛보기 요청/답변이 보인다.
- 모바일과 데스크톱 폭에서 레이아웃이 깨지지 않는다.
- 정적 랜딩 외의 localStorage, 인증, 백엔드 기능이 포함되지 않는다.

자동화는 프로젝트 생성 후 가능한 범위에서 실행한다.
예상 검증은 lint, typecheck, build, 브라우저 확인이다.

## Deferred Decisions

- 다음 본문 route를 `/today`로 확정할지 여부.
- `웹에서 시작하기`를 첫 PR에서 `/today` 링크로 둘지, 준비 중 상태로 둘지 여부. 현재 추천안은 첫 PR에서는 준비 중 상태다.
- localStorage 프로토타입의 정확한 상태 모델과 파일 구조.
- 샘플 활동 지표의 숫자와 맛보기 문구.

## Implementation Sequence

1. 이 스펙을 승인받는다.
2. 새 worktree를 만들고 보일러플레이트 생성 브랜치를 만든다.
3. Next.js, React, TypeScript, Tailwind CSS 기반 프로젝트 보일러플레이트만 생성한다.
4. 보일러플레이트의 lint, typecheck, build가 가능한지 확인한다.
5. 보일러플레이트 변경을 먼저 PR로 남긴다.
6. 그 다음 별도 구현 브랜치에서 `/` 정적 랜딩 구현 계획과 작업을 진행한다.
