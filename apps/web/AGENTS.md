# apps/web — 온설 공개 사이트

Project-wide rules live in the root `AGENTS.md`.

## Shared code with apps/admin

Split across three packages by kind, not lumped into one: `ActionConfirmDialog`/`QueryProvider` live in `packages/ui` (imported as `"ui/..."`), `apiFetch`/`ApiError`/`login`/`logout`/`fetchCurrentUser`/`CurrentUser` live in `packages/api` (imported as `"api"`), `formatTimestamp` lives in `packages/utils` (imported as `"utils"`) — all byte-identical between this app and `apps/admin`. See `docs/decisions/2026-08-25-onseol-shared-ui-package-decisions.md` for what's shared vs. kept local and why (short version: only things genuinely identical in both apps with no reason to diverge get shared — `signup`/`googleLoginUrl`/auth hooks/day-formatting helpers stay here since apps/admin either doesn't need them or needs a structurally different version). `app/lib/api.ts` and `app/lib/format.ts` are thin re-export shims over `api`/`utils` plus this app's own additions — don't move their remaining local exports into a shared package without checking apps/admin actually needs them too.

Before adding a new component/util/type that feels generic, check whether `apps/admin` would plausibly use the exact same thing — if yes, put it in `packages/ui` from the start rather than duplicating and extracting later.

## Storybook

This app does **not** run Storybook — that lives in `apps/storybook-app` (see `apps/storybook-app/AGENTS.md`, `docs/decisions/2026-08-26-onseol-storybook-app-decisions.md`). `.stories.tsx` files for this app's own components (e.g. `app/today/components/NoteCard.stories.tsx`) still live here, right next to the component they document — only the Storybook runner/config moved out. `@storybook/nextjs-vite`, `storybook`, and `eslint-plugin-storybook` stay as devDependencies here so those story files still typecheck/lint as part of this app's own `pnpm --filter web typecheck`/`lint` — don't remove them just because `pnpm --filter web storybook` no longer exists.

Tailwind v4's class-scanning is directory-scoped, so `app/globals.css`'s `@source "../../../packages/ui/src";` line is required for `packages/ui` components' Tailwind classes to generate wherever this file gets imported (including from `apps/storybook-app`, which imports this exact file) — don't remove it even if nothing in this app's own source appears to need it.

## Account area: 내 정보 / 내 기록 (split, not one /me page)

Originally one `/me` page held identity info, the nickname section, and the answer log together. Split (2026-08-29, user feedback: "내가 남긴 답변, 닉네임 수정을 모두 /me 에 넣지않고 분리") into separate routes, each its own thin page + self-contained section component(s) that call `useAuth()`/query hooks themselves (no props from the page, matching the pattern already established by `MyAnswerLogSection`):

- `/me` (`app/me/page.tsx`) — **내 정보**: email + joined date, plus `NicknameSection` (`app/me/components/`) — nickname is profile identity, not a system setting, so it stays here rather than under a separate settings route.
- `/records` (`app/records/page.tsx`, a server component wrapping `RecordsPageContent.tsx` in `<Suspense>` — required because that content component calls `useSearchParams()`, following the same split `reset-password/page.tsx` already uses) — **내 기록**: two sections behind tabs (`RecordsTabs.tsx`, local to this route — not extracted to `packages/ui`, since only one place uses it so far), not stacked on one long page — got too long once both existed together (2026-08-29 user feedback). `MyRequestLogSection` ("내가 남긴 고민", the default tab) is the viewer's own posted requests, each with every reply they received nested (`RequestLogCard`, `app/lib/requests/api.ts`'s `fetchMyRequestLog` → `GET /requests/mine`); reply authors render via `authorDisplayLabel(reply.author, "익명")`, a flat fallback (no `authorSlot` disambiguation needed here — unlike `/read`, this is a private per-viewer list, not a shared thread). `MyAnswerLogSection` ("내가 남긴 답변", replies the viewer gave to others) is the other tab. The active tab is seeded from a `?tab=` search param (shareable/bookmarkable) into local `useState`, not derived from the search param on every render — a click updates both, but rendering only depends on the state, so tab-switching doesn't rely on the router actually round-tripping (it's mocked as a no-op in tests). Only the active tab's section is mounted, so the inactive one's query simply doesn't fire — no manual `enabled` flag needed on either query hook. Future pagination/infinite-scroll per tab was the reason tabs (not stacking) were chosen — see `docs/decisions/2026-08-29-onseol-records-tabs-decisions.md`.

There is deliberately no `/settings` route yet (user feedback, same round: "설정은 서비스 시스템 관련된걸 생각하고 있어서" — settings is reserved for future service/system-level config, not profile fields like nickname). Add it back once there's an actual system setting to put there, rather than standing up an empty page now.

`app/components/navigation/routes.ts` has two separate arrays, not one: `serviceNavItems` (public — 남기기/답하기/온설 읽기, shown to guests too) and `accountNavItems` (내 정보/내 기록 — member-only). `ServiceNav.tsx`'s profile dropdown renders `accountNavItems` as its own links (plus 로그아웃); the mobile hamburger menu concatenates `serviceNavItems` with `accountNavItems` only when `status === "authenticated"`. Don't put a member-only destination into `serviceNavItems` — it's rendered in the always-visible desktop nav bar with no auth gating of its own.

`RequestComposer` (`/today`) and `AnswerComposer` (`/answer`) both show a reveal toggle ("닉네임(닉네임)으로 남기기"), but **only when `user.nickname` is set** — a guest or a nicknameless member never sees it at all, since the backend would reject/ignore the choice anyway (see `apps/api-server/AGENTS.md`'s "Nicknames" section). The toggle itself is `packages/ui`'s `Toggle` component (`ui/Toggle`), not a raw `<input type="checkbox">` — a real checkbox under the hood (native keyboard/focus/label semantics), styled as a switch via Tailwind `peer-checked:` variants; reach for this anywhere else a boolean setting needs a switch UI instead of styling another one-off checkbox. `app/lib/author-label.ts`'s `authorDisplayLabel(author, fallbackLabel)` is the one place that decides "real nickname vs. anonymous fallback label" — used by both `/read` (`ReadThread`, fallback is the `authorSlot`-based label) and `/answer` (`AnswerLog`, fallback is the session-counter "익명 N" label); don't reimplement this decision at a new call site. `RequestDto`/`ReplyDto`/`FeedReplyDto`/`MyAnswerLogEntryDto` all carry an `author`/`requestAuthor`/`replyAuthor: AuthorDisplayDto` field (`app/lib/requests/api.ts`) mirroring the backend's discriminated union — `authorId`/`guestId` themselves still never cross the boundary. See `docs/decisions/2026-08-28-onseol-nickname-post-reveal-frontend-decisions.md`.

Changing an already-set nickname has a server-enforced cooldown, default 7 days but admin-tunable (see `apps/api-server/AGENTS.md`'s "Nicknames" section) — `CurrentUser.nicknameChangeAvailableAt` (ISO string, `null` if never changed) lets `NicknameSection` disable the edit button and show "N일 후에 다시 바꿀 수 있어요." proactively, not just surface the 429 after a failed attempt. See `docs/decisions/2026-08-29-onseol-nickname-cooldown-decisions.md`.

## Public profile page (`/u/[slug]`)

Every place a revealed nickname is shown (`ReadRequestBubble`/`ReadReplyBubble` on `/read`, `RequestBubble` on `/answer`, `RequestLogCard` on `/records`) links it to `/u/[slug]` — `app/lib/author-label.ts`'s `authorProfileHref(author)` returns `null` for an anonymous author (rendered as plain `<p>`, no link) or `` /u/${nickname}-${discriminator} `` (URI-encoded) otherwise; each bubble component takes an optional `authorHref` prop alongside `authorLabel` and conditionally wraps the label in a `next/link` `<Link>`. `app/lib/profile/slug.ts`'s `parseProfileSlug` reverses this — it matches the **last** `-XXXX` (4 hex chars) anchored at the end of the slug, not the first, so a nickname that itself contains a hyphen still parses correctly.

`app/u/[slug]/page.tsx` is a client component using `useParams()` (not `useSearchParams()`, so unlike `/records` it doesn't need a `<Suspense>`-wrapped server-component split — see "Account area" above for that pattern where one *is* needed). Public — no auth required or checked, matching `/read`. Backed by `GET /users/:nickname/:discriminator` (`apps/api-server`'s `ProfileModule` — see that app's `AGENTS.md`), which already filters to only what the account revealed and is still visible; the frontend does no additional filtering, just renders `requests`/`replies` as returned. A malformed slug, a 404 (no matching account, including a stale link after someone renamed/cleared their nickname), and a generic fetch failure each get their own message — not a blank page or a thrown error.

### Visibility settings (`/me`)

Three cards, three components, one shared save mechanism. `NicknameSection` (닉네임 텍스트/쿨타임만) is a plain standalone `<form>`, unrelated to the other two. `NicknameVisibilitySection` ("닉네임 공개") and `ProfileVisibilitySection` ("내가 남긴 고민/답변 목록 공개", "고민/답변 개수 공개" — last one renamed from a bare "개수 공개," which read as ambiguous alone) each get their own card but share one draft/save/dialog via `VisibilityDraftProvider` (`app/me/components/`), which wraps just those two in `MePage`. Splitting "닉네임 공개" out of `NicknameSection` into its own card (rather than nesting it in the nickname card, or merging all four switches into one card) was a direct user correction — see the decision doc for the two rounds that got this wrong first: physically merging all four into one card, then just moving the toggle without separating it from the nickname text form.

`useVisibilityDraft()` is how `NicknameVisibilitySection`/`ProfileVisibilitySection` read their own field(s) and report a change, via `setField(field, value)` — a new visibility switch should plug into this from wherever it visually belongs, not reimplement its own draft/save/dialog. Flow is edit → 저장 → confirm dialog → applied, not immediate-fire: toggling only updates the shared `draft` (`useState` inside the provider, lazily initialized from the `user` prop it's given) — no API call until confirmed. Whenever `draft` differs from `user` on any field, a fixed bar appears pinned to the bottom of the page with "저장"/"취소". "저장" is `type="submit"` on a real `<form>` (`VisibilityDraftProvider` wraps `{children}` + the bar in one) — safe here specifically because `NicknameSection`'s own text-edit `<form>` lives outside this provider as a sibling in `MePage`, so nothing nests; multiple independent `<form>` elements on one page is fine, only nesting one inside another is invalid HTML. Submitting opens `ui/ActionConfirmDialog` ("설정을 저장할까요?") rather than saving directly; confirming there sends the whole draft in one `PATCH /auth/profile-visibility` call. The bar's "취소" (`type="button"`) reverts `draft` to `user`'s values with no dialog — only the save path has a consequence to confirm. A persistent `<div aria-live="polite" className="sr-only">` (always mounted, separate from the bar's own conditionally-rendered text) announces dirty/error/"설정이 저장되었습니다." — it has to be a permanent element, not part of the bar's conditional subtree, because the bar itself unmounts the instant a save succeeds (`isDirty` flips back to `false`), which would otherwise delete the "saved" announcement before assistive tech reads it.

`ProfileVisibilitySection`'s three toggles are `disabled` (not hidden) whenever `!user?.nickname || !draft.nicknameVisible` — reactive to the *draft*, not just the saved value, so flipping "닉네임 공개" off immediately disables them before saving. This is because `/u/[slug]` 404s for everyone once the nickname is hidden or doesn't exist (`UsersService.findByNicknameAndDiscriminator`), so those three switches have no effect while disabled; a `text-amber-600` note under the section heading explains why. Their saved values are left untouched while disabled and simply resume mattering once the nickname is shown again — no backend change needed for this, it's purely a "don't let people fiddle with settings that currently do nothing" frontend nicety.

`NicknameVisibilitySection`'s toggle used to be a "지우기" button that actually cleared the nickname via `DELETE /auth/nickname` — the user caught that as wrong, since clearing reset the change-cooldown too, so hide-then-immediately-set-a-new-nickname bypassed it entirely. `nicknameVisible` is a pure visibility switch instead: the underlying nickname and its cooldown are completely unaffected either way, and un-hiding always brings back the exact same nickname. See `docs/decisions/2026-08-30-onseol-profile-privacy-decisions.md` for the full "지우기 → 감추기" writeup and the later save-flow/card-split revisions.

`PublicProfileDto` (`app/lib/profile/api.ts`) carries `requestsVisible`/`repliesVisible`/`countsVisible` booleans plus `requestCount`/`replyCount` (`number | null` — `null` exactly when `countsVisible` is `false`); `/u/[slug]`'s `ProfileSection` component (not exported, local to `page.tsx`) is what actually decides "empty vs. hidden" — a hidden list shows `hiddenMessage`, a visible-but-empty list shows `emptyMessage`, since the backend always returns `[]` for both cases and only the boolean tells them apart. The count renders as a `"(N)"` suffix directly in each section's `<h2>` (e.g. "남긴 고민 (3)"), not as a separate summary line — omitted entirely (no heading suffix at all) when `countsVisible` is `false`, and shown regardless of whether that section's own list is visible (`countsVisible` is independent of `requestsVisible`/`repliesVisible`).

`vitest.setup.ts`'s global `next/navigation` mock defines `useParams` as `vi.fn(() => ({}))` specifically so this page's tests can override it per-test via `vi.mocked(useParams).mockReturnValue({ slug: "..." })` — the other mocked hooks there (`useRouter`, `usePathname`, `useSearchParams`) stay plain functions since nothing currently needs to override them per-test.
